## Purpose

`data/catalog/domain/flora/` is the canonical responsibility placement for governed Flora-domain catalog records and indexes at the `CATALOG / TRIPLET` lifecycle stage. Records here are intended to connect stable botanical identities and products to source roles, evidence, rights, sensitivity posture, receipts, catalog projections, release state, correction lineage, and rollback targets.

Candidate record families include plant taxa, specimens, occurrences, vegetation communities, invasive plants, phenology observations, restoration context, crosswalks, and public-safe Flora products. Listing a family does not prove that its records, contract, schema, validator, evidence, or release state exist.

## Authority level

**Canonical responsibility placement for Flora domain catalog records / repository-grounded draft / concrete catalog profile and realization PROPOSED / not truth, evidence, policy, release, or publication authority.**

This lane may carry catalog descriptors and governed references. It cannot replace Flora semantics under `contracts/`, machine shape under `schemas/`, admissibility under `policy/`, source identity and rights under `data/registry/`, process memory under `data/receipts/`, EvidenceBundles and proof support under `data/proofs/`, release decisions under `release/`, or public-safe carriers under `data/published/`.

## What belongs here

| Accepted family | Required posture |
|---|---|
| Flora domain catalog records | Stable identity, object family, source role, spatial and temporal scope, lifecycle state, and release state |
| Flora domain catalog indexes | Steward-facing or release-linked discovery; never an ungoverned public shortcut |
| Taxon, specimen, and occurrence descriptors | Explicit taxonomic concept, observation or specimen role, source, evidence, sensitivity, and time semantics |
| Vegetation-community descriptors | Public-safe or controlled catalog context without replacing Habitat, Land Cover, Soil, or Hydrology truth |
| Invasive-plant and phenology descriptors | Time-bounded object role, evidence, uncertainty, source, and release context |
| Restoration-context descriptors | Cross-domain references that preserve each domain's authority and do not infer causality by co-location |
| Evidence and source pointers | Resolvable EvidenceRef, EvidenceBundle, SourceDescriptor, and applicable registry references |
| Sensitivity and transform pointers | Tier, restriction, reason, PolicyDecision, ReviewRecord, public-safe derivative, and RedactionReceipt or accepted equivalent |
| Catalog quality summaries | Derived summaries that cite validation reports, receipts, input digests, and output digests |
| Release, correction, and rollback pointers | Immutable governed references without duplicating release or rollback authority here |

Records should be deterministic where practical, bounded in scope, correctable, and explicit about whether they are internal candidates, reviewable records, release-linked records, withdrawn records, or historical records.

## Inputs

Catalog inputs should be governed references and validated derivatives, not raw truth by placement:

- processed Flora object identities, versions, and digests;
- source and dataset registry references with role, rights, sensitivity, spatial and temporal scope, and retrieval context;
- contracts, schemas, catalog profiles, policy decisions, and review records;
- EvidenceRef-to-EvidenceBundle resolution and applicable proof support;
- `CatalogBuildReceipt`, `RunReceipt`, `ValidationReport`, transform, redaction, correction, and release-support receipts;
- STAC, DCAT, PROV, and triplet references when projections exist;
- immutable release, correction, withdrawal, supersession, and rollback references.

Unknown source role, taxonomic concept, rights, sensitivity, evidence, transform, policy, review, release, correction, or rollback state holds a record from public-bound use.

## Outputs

This lane may emit or support:

- internal or reviewable Flora catalog records;
- deterministic Flora domain indexes and catalog subsets;
- release-linked catalog descriptors that reference, but do not replace, release authority;
- inspectable agreement inputs for STAC/DCAT/PROV/domain/triplet closure;
- correction- and rollback-aware discovery metadata for governed APIs and review tools.

Catalog placement is not publication. Public clients receive only policy-safe, release-approved representations through governed interfaces and public-safe carriers.

## Flora catalog requirements

The following are **PROPOSED requirements** until accepted profiles, emitted records, deterministic validators, negative fixtures, required workflows, and observed release behavior prove them:

| Requirement | Minimum meaning |
|---|---|
| Stable catalog identity | Deterministic identifier for the Flora object or product; version and digest changes remain explicit |
| Botanical object and knowledge character | Taxon, taxonomic concept, specimen, occurrence, vegetation community, invasive record, phenology observation, restoration context, or derived-product role remains distinct |
| Taxonomy and vocabulary reference | Accepted identifier system, concept/version, name usage, rank, synonym or crosswalk status, and unresolved ambiguity remain explicit |
| Spatial and temporal support | Geometry or generalized geography, coordinate reference, observation/collection/valid/retrieval/release/correction times, precision, and coverage limits remain explicit |
| Source and rights reference | SourceDescriptor, dataset/version, source role, license/terms, retrieval context, and rights decision resolve |
| Evidence reference | Claim-bearing fields resolve EvidenceRef to EvidenceBundle; unsupported claims cite-or-abstain |
| Sensitivity and transform reference | Tier, restriction, public-safe transform, reason code, PolicyDecision, ReviewRecord, and RedactionReceipt or accepted equivalent resolve where material |
| Receipt reference | Build, validation, transform, redaction, correction, and release-support operations remain auditable |
| Catalog closure | Domain, STAC, DCAT, PROV, triplet, evidence, and release views agree on identity, digest, source role, scope, access, and release reference |
| Release and correction reference | Public-bound records point to immutable ReleaseManifest, public scope, correction or withdrawal state, and rollback target |

Candidate catalog records must not masquerade as released records. Released records must remain distinguishable from corrected, withdrawn, superseded, or historical records without rewriting prior history.

## Sensitivity guardrails

| Guardrail | Required posture |
|---|---|
| Catalog carriers are not source truth | Resolve claims to evidence and source records; do not infer truth from directory placement or presentation quality |
| Exact rare or protected plant locations fail closed | Deny, restrict, embargo, generalize, aggregate, or redact precise locality according to rights, policy, review, and release state |
| Culturally sensitive knowledge is not a public default | Respect authority, consent, obligations, traditional-knowledge labels where applicable, minimum-necessary representation, and rights-holder review |
| Join-induced sensitivity is real sensitivity | Evaluate re-identification and harm created by taxon, parcel, specimen, collector, landowner, habitat, hydrology, infrastructure, temporal, and cross-domain joins |
| Public derivatives require transform evidence | Preserve input and output digests, method/version, precision loss, reason, policy context, review, and RedactionReceipt or accepted equivalent |
| Source quality does not override sensitivity | Authoritative or high-quality data can still be restricted; unknown rights or sensitivity deny public-bound use |
| Watchers do not publish | Source-head checks, watchers, alerts, and candidate builders may propose work; they do not admit, release, or publish catalog records |
| Unreleased is not public | Existence in this directory, a green check, a catalog index, or a render does not create public authority |
| AI remains interpretive | AI summaries and classifications are candidates or carriers, never root truth; resolve evidence and apply policy, review, release, correction, and rollback first |

## Migration, correction, and rollback

Use reversible, receipt-backed change:

1. identify the affected catalog identity, digest, projection set, release reference, and public carriers;
2. quarantine or hold contradictory, stale, sensitive, rights-unclear, or invalid candidates;
3. issue correction, withdrawal, or supersession state without rewriting prior history;
4. regenerate and validate affected domain, STAC, DCAT, PROV, triplet, evidence, and release references;
5. obtain required policy, rights, sensitivity, domain, release, and rollback review;
