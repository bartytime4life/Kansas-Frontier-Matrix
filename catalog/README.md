## Purpose

`catalog/` exists only as a deprecated containment and compatibility surface for historical root-level catalog-family paths.

Its purpose is to:

- keep legacy links visible while consumers are discovered and migrated;
- state the canonical destination for each object family;
- prevent new authority or payloads from hardening at the root;
- preserve correction and rollback context during convergence; and
- support eventual retirement after independently verified zero-producer and zero-consumer closure.

The long-term target is retirement, not continued growth. This README does not move, rename, delete, regenerate, release, or publish any descendant.

## Authority level

**CONFIRMED existing path / CONFIRMED adopted `deprecated` class / non-authoritative / migration-bound.**

The accepted Directory Rules classify `catalog/` as a deprecated containment root. The active Root Registry projects that decision as:

- `root_id`: `root.catalog`;
- `class`: `deprecated`;
- `status`: `DEPRECATED`;
- `canonical_target`: `data/catalog/`;
- `mutation`: `immutable`;
- validation profiles: `frozen_no_writes` and `redirect_only`;

This root owns no KFM truth, catalog semantics, machine shape, policy, lifecycle state, evidence, receipts, proofs, release decisions, rollback authority, published bytes, implementation, runtime behavior, or public interface.

## What belongs here

Only the minimum material needed to preserve a deprecated redirect surface:

- the root and descendant redirect READMEs already tracked;
- the existing zero-byte `.gitkeep` placeholders until a reviewed migration removes them; and
- links to authoritative migration, alias, correction, rollback, and retirement records stored in their governing roots.

Do not add new placeholders. A README or `.gitkeep` does not establish implementation, maturity, authority, or a durable reason to retain a speculative directory.

## What does NOT belong here

The following are prohibited:

- catalog records, STAC items, DCAT distributions, PROV records, indexes, manifests, or domain catalog instances;
- graph, relationship, or triplet bundles;
- source, dataset, layer, rights, or sensitivity registry records;
- receipts, proofs, attestations, signatures, release manifests, promotion decisions, correction notices, or rollback cards;
- RAW, WORK, QUARANTINE, PROCESSED, CATALOG, TRIPLETS, or PUBLISHED data instances;
- semantic contracts, JSON Schemas, policy rules, validators, pipelines, application code, runtime adapters, workflows, or configuration;
- generated public products, tiles, PMTiles, COGs, GeoParquet, exports, caches, search indexes, or AI payloads;
- credentials, secrets, restricted data, sensitive geometry, or protected source material.

## Migration and retirement

1. Freeze the governing commit, Directory Rules digest, Root Registry entry, and complete tree.
2. Create or update the governed drift and path-decision record without changing authority by projection alone.
3. Inventory repository, ignored, generated, hosted, database, object-storage, package, cache, API, map, export, search, and AI references.
4. Classify every reference by object family, authority owner, lifecycle stage, rights, sensitivity, and release state.
5. Accept the structural retirement or migration decision required by adopted Directory Rules.
6. Map every old path and fragment to one governed target; preserve stable identities and digest lineage.
7. Cut over producers first, then consumers, then indexes, caches, documentation, exports, and public/semi-public surfaces.
8. Validate data and reference parity, evidence closure, policy outcomes, release state, correction propagation, and replay behavior.
9. Rehearse rollback to the pre-migration state without restoring a writable parallel authority.
10. Remove placeholders and descendant redirects only after a measured compatibility window.
11. Retire the root only after zero-producer, zero-consumer, link, host, cache, external, and rollback checks pass.
12. Record the retirement receipt and retain the historical identity in Git and governance registers.

No step may silently convert documentation cleanup into a release, migration, or deletion decision.
