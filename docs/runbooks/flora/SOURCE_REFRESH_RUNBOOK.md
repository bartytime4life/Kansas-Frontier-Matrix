> [!IMPORTANT]
> **Refresh is not source admission.** This procedure may recheck and capture only a source product whose current `SourceDescriptor`, activation/admission decision, rights, sensitivity, access, cadence, exact product identity, and connector boundary have already been accepted. Repository presence, a README, a placeholder YAML file, a schema-valid fixture, a connector scaffold, a successful HTTP response, or a prior release does not supply that authority.

> [!WARNING]
> **Live Flora source refresh is `HOLD` at this evidence snapshot.** The inspected subtype-first Flora source-registry lane contains one `PROPOSED` placeholder rather than a complete admitted `SourceDescriptor`; the source-authority projection is empty and implementation-absent; `connectors/flora/` is documentation-only; source-first connector paths remain draft or conflicted; Flora policy is scaffolded and evaluator-unbound; and the sensitivity lane is a scaffold. The current executable Flora proof is synthetic, public-safe, and no-network only.

> [!CAUTION]
> **Exact or inferable sensitive plant locations fail closed.** Rare, protected, threatened, culturally sensitive, steward-controlled, commercially vulnerable, or collection-sensitive plant records must not be deobscured, logged into public channels, joined into reverse-engineerable products, or treated as public-ready because retrieval succeeded. Upstream obscuration is a minimum protection, not permission to infer the hidden location.

> [!NOTE]
> **KFM is not an official botanical, conservation-status, foraging, poison-control, land-access, regulatory, emergency, or life-safety authority.** Use issuing agencies, responsible institutions, rights holders, and qualified stewards for current determinations and operational instructions.

## 1. Purpose, scope, and non-goals

### 1.1 Purpose

Use this runbook only when a previously governed Flora source and an exact named source product are due for a bounded recheck, and a current accepted source-refresh implementation exists for that product.

The procedure helps an operator:

1. freeze the exact repository, descriptor, activation decision, source product, endpoint, request, temporal scope, rights, sensitivity, prior source head, and connector context;
2. decide whether any live request is currently authorized;
3. execute only the approved change-detection and retrieval behavior;
4. preserve source-native bytes and response metadata without silently normalizing names, coordinates, taxonomy, statuses, or claims;
5. route the result to a governed `RAW` or `QUARANTINE` handoff;
6. produce or reference the required source-run or capture receipt through an accepted writer;
7. stop before `WORK`, `PROCESSED`, `CATALOG / TRIPLET`, proof, release, deployment, or publication;
8. hand downstream work to the owning taxonomy, pipeline, evidence, policy, review, correction, and release procedures.

### 1.2 Lifecycle boundary

KFM's lifecycle remains:

```text
SOURCE EDGE / ADMISSION
    -> RAW
    -> WORK / QUARANTINE
    -> PROCESSED
    -> CATALOG / TRIPLET
    -> PUBLISHED
```

This runbook controls only the bounded edge shown below:

```mermaid
flowchart LR
    A["Accepted SourceDescriptor<br/>+ activation/admission decision"] --> B["Approved source-product-specific<br/>change detector / connector"]
    B --> C{"Bounded outcome"}
    C -->|no material change| D["NO_CHANGE receipt / handoff"]
    C -->|authorized capture| E["RAW capture candidate<br/>immutable bytes + metadata"]
    C -->|unresolved or restricted| F["QUARANTINE handoff<br/>reason + review requirement"]
    C -->|insufficient authority| G["HOLD / ABSTAIN / DENY"]
    C -->|technical failure| H["ERROR"]
    E --> I["Downstream pipeline handoff"]
    F --> J["Steward review"]
    I -. "separate procedures" .-> K["WORK -> PROCESSED<br/>-> CATALOG / TRIPLET"]
    K -. "separate release decision" .-> L["PUBLISHED"]

    classDef hold fill:#f8d7da,stroke:#b42318,color:#111;
    classDef gate fill:#fff3cd,stroke:#9a6700,color:#111;
    classDef ok fill:#dff7e5,stroke:#1a7f37,color:#111;
    class C gate;
    class D,E,I ok;
    class F,G,H,J hold;
```

### 1.3 In scope

- refresh preflight for an already admitted source product;
- source family, exact product, access path, and request-scope freeze;
- source-product-specific conditional, version, manifest, cursor, or inventory-based change detection;
- bounded retrieval through an accepted connector;
- integrity, completeness, response-metadata, and source-head capture;
- source-edge rights, sensitivity, cultural-knowledge, and source-role checks;
- routing to approved Flora `RAW` or `QUARANTINE` interfaces;
- no-change, capture, quarantine, hold, abstain, deny, error, and cancellation handoffs;
- source-run or capture receipt requirements;
- stale-source evidence and source-product supersession handoff;
- downstream invalidation or correction notification when a refresh reveals a material change.

### 1.4 Out of scope

This runbook does not:

- discover or onboard a new source;
- create, approve, or edit a `SourceDescriptor`;
- turn `data/registry/sources/flora/usda_plants.yaml` into an admitted descriptor;
- resolve the parallel source-registry topology;
- activate a connector or source;
- choose a live endpoint, API version, cadence, terms, credential, or rate limit from memory;
- infer, upgrade, downcast, or silently translate `source_role`;
- decide accepted taxonomy, synonymy, nativity, invasiveness, conservation status, or current presence;
- normalize source-native records;
- infer presence from taxonomy, county distribution, a model, a checklist, or habitat context;
- perform a public geoprivacy transform;
- expose culturally sensitive plant knowledge or collection-security information;
- create an `EvidenceBundle`, `PolicyDecision`, `ReviewRecord`, proof pack, catalog record, graph edge, or release manifest;
- write directly to `WORK`, `PROCESSED`, `CATALOG`, `TRIPLET`, `PUBLISHED`, proof, registry, or release state;
- invalidate public caches autonomously;
- publish maps, tiles, APIs, dashboards, exports, alerts, stories, or AI answers;
- approve correction, withdrawal, rollback, release, deployment, promotion, or publication.

> [!IMPORTANT]
> If requested work includes source admission, taxonomy resolution, normalization, evidence resolution, public-safe transformation, release, or correction, split those transitions into their owning review boundaries. Do not stretch this runbook across them.

## 3. Refresh state and source-product vocabulary

### 3.1 Keep the state axes separate

A source refresh crosses several independently governed state systems. Never compress them into one `active`, `valid`, or `published` flag.

| State axis | Example values | Owner | This runbook may change it? |
|---|---|---|---:|
| Source admission | proposed, admitted, denied, retired, superseded | Source-governance authority | No |
| Connector activation | disabled, fixture-only, live candidate, live active, quarantined, retired | Connector/source authority | No |
| Retrieval | not requested, no change, captured, partial, failed | Connector operator | Yes, within accepted scope |
| Lifecycle | source edge, RAW, WORK, QUARANTINE, PROCESSED, CATALOG / TRIPLET, PUBLISHED | Data and release controls | Only source-edge handoff to RAW or QUARANTINE |
| Evidence | unresolved, candidate, supported, superseded, withdrawn | Evidence authority | No |
| Rights | verified open, verified restricted, permission required, unknown, denied | Rights authority | No |
| Sensitivity | public, restricted, sensitive location, culturally sensitive, steward controlled, unknown review required | Sensitivity/steward authority | No |
| Taxonomy | raw name, candidate concept, reconciled, ambiguous, superseded | Taxonomy authority | No |
| Review | draft, needs review, reviewed, approved, rejected, superseded | Assigned reviewer | No |
| Release | not released, candidate, released, deprecated, withdrawn | Release authority | No |
| Correction | none, investigation open, corrected, superseded, withdrawn, rollback pending | Correction/release authority | No |

A refresh may return `RAW_CAPTURED` while evidence is unresolved, rights are restricted, taxonomy is ambiguous, and release remains `not_released`. Those states are not contradictory.

### 3.2 Source family is not source product

A family name does not identify what was retrieved.

| USDA PLANTS | Which database export, checklist, county/state distribution table, taxonomy snapshot, version, vintage, and format? |
| GBIF | Which occurrence download, query predicate, download key, dataset/publisher set, record filters, taxon scope, and citation package? |
| iNaturalist | Which observation export or API query, project, taxon scope, quality state, license filter, obscuration posture, cursor, and time window? |
| iDigBio / Symbiota / herbarium portal | Which collection export, institution/collection codes, specimen subset, media bundle, georeference fields, and version? |

| Vegetation survey | Which survey protocol, plot/community product, project, season, schema, spatial support, and steward? |
| Restoration record | Which project registry, planting record, establishment observation, monitoring product, rights posture, and site-precision rule? |

### 3.3 Access path is not evidence role

- GBIF, iDigBio, Symbiota, and other aggregators or portals may distribute records from originating publishers.
- A portal response does not upgrade the portal to specimen, observation, legal-status, or stewardship authority.
- Preserve originating dataset, institution, collection, publisher, license, basis of record, record identifier, and record-level limitations.
- A taxonomic checklist or county distribution table is not a precise occurrence.
- A specimen is not automatically current presence.
- A regulatory listing is not an observation.
- A vegetation index or suitability model is not a field observation.
- Habitat, soil, hydrology, land cover, agriculture, roads, and settlement data are covariates or context unless separately admitted for a permitted claim.

## 7. Source refresh procedure

### Step 1 — Open the refresh record and freeze authority

**Goal:** establish exact scope before side effects.

1. assign a run identifier through the accepted mechanism;
2. record operator, trigger, base commit, runbook blob, descriptor reference, activation reference, product identity, request digest, connector version, and prior source head;
3. verify no overlapping run, correction, migration, or active branch owns the same source-product head;
4. resolve the kill switch and escalation path;
5. return `HOLD` if any required freeze field is unresolved.

Do not derive authority from this runbook, a watcher alert, or a scheduler tick.

### Step 2 — Resolve and validate the exact SourceDescriptor

**Goal:** prove that a complete current descriptor exists.

1. resolve the descriptor from the accepted registry interface;
2. reject documentation-generated placeholders;
3. verify descriptor version and digest;
4. validate with the current declared validator;
5. verify `domain_scope` includes Flora where required;
6. preserve the exact `source_role`;
7. verify review, lifecycle, connector, and release fields without treating them as a single approval;
8. resolve the separate activation/admission decision.

Current repository evidence includes the validation command:

```bash
python tools/validators/sources/validate_source_descriptor.py
```

A pass proves schema conformance only. It does not prove live reachability, terms, rights, sensitivity, activation, botanical claims, or release.

### Step 3 — Reverify terms, rights, sensitivity, cultural authority, and cadence

**Goal:** prevent stale governance metadata from authorizing a new capture.

Check:

- current source terms and version;
- license or terms URL and retrieved copy/reference;
- attribution requirements;
- redistribution and commercial-use posture;
- credential/account conditions;
- record-level and media-level license behavior;
- embargo, suppression, deletion, and takedown behavior;
- rare/protected taxon handling;
- upstream obscuration and coordinate uncertainty;
- locality text, collection notes, specimen images, collector information, and private-property clues;
- culturally sensitive plant knowledge and authority to control;
- cadence, freshness expectation, source timezone, and known update window;
- source-specific restrictions on automation, bulk access, caching, or derivative products.

If any condition changed, return `HOLD` or `DENY` and route descriptor/activation review. Do not update the descriptor inside this run.

### Step 4 — Rehearse the accepted implementation without network access

**Goal:** prove deterministic boundaries before live contact.

Run the current bounded Flora fixture suite where applicable:

```bash
KFM_NO_NETWORK=1 PYTHONDONTWRITEBYTECODE=1 \
python -m unittest discover \
  --start-directory tests/domains/flora \
  --pattern 'test_flora_smoke.py' \
  --verbose
```

This suite is not a live connector test. A complete source-product refresh implementation also needs product-specific fixtures that prove:

- exact request construction;
- no-change behavior;
- changed response behavior;
- pagination/cursor/manifest completeness;
- mixed record-level rights;
- source-role preservation;
- upstream obscuration preservation;
- exact-location and transform-secret non-disclosure;
- schema/content-type drift;
- partial transfer and timeout behavior;
- cancellation and retry behavior;
- RAW/QUARANTINE writer failure;
- receipt failure and readback mismatch.

Do not install or activate a live connector merely to satisfy the rehearsal.

### Step 5 — Perform approved change detection

**Goal:** determine whether a bounded retrieval is necessary.

Use only the detector accepted for the exact source product:

| Detector | Appropriate when | Required caution |
|---|---|---|
| HTTP ETag / conditional GET | The accepted endpoint documents stable representation validators. | Weak/strong semantics, redirects, auth variants, content negotiation, and query scope must be frozen. |
| Last-Modified / conditional GET | The endpoint documents reliable modification time. | Clock, granularity, timezone, and server behavior may miss changes. |
| Release/version identifier | The publisher exposes a stable product release or dataset version. | Product identity must not be confused with page or API software version. |
| Manifest or checksum | The publisher exposes a complete, stable manifest or digest. | Verify algorithm, canonicalization, coverage, and signature/transport. |
| API cursor / updated-since token | The API guarantees cursor ordering and replay. | Handle deletion, reprocessing, late records, pagination, and cursor expiry. |
| Archive inventory | The source publishes a stable file/object inventory. | Compare members, sizes, versions, tombstones, and digests—not only archive filename. |
| Event feed | The source publishes authoritative change events. | Events are signals; verify the referenced product state. |
| Bounded full recapture | No trustworthy incremental detector exists and terms permit it. | Requires explicit size, cost, cadence, rate-limit, and snapshot-review approval. |

Record request scope, detector inputs, response status, response headers allowed by policy, observed time, and source-head identity.

#### `304 Not Modified` rule

A `304` or equivalent may support `NO_CHANGE` only for the exact request and representation semantics. It does not prove:

- rights are still valid;
- source role is correct;
- sensitivity classification is current;
- taxonomy is stable;
- record deletions outside the query did not occur;
- evidence remains sufficient;
- a public release is fresh;
- a prior release remains approved.

Do not renew governance timestamps merely because bytes did not change.

### Step 6 — Retrieve and preserve source-native material

**Goal:** acquire only the approved product without interpretation.

- use the accepted connector and credential reference;
- enforce scope, rate limits, timeout, maximum bytes/records/pages, redirects, content types, and host allowlist;
- prevent SSRF, local-file, metadata-service, and internal-network access;
- stream into the accepted capture mechanism;
- preserve source-native bytes or immutable source references;
- preserve response metadata needed for replay;
- preserve archive members and order where material;
- preserve publisher, dataset, collection, institution, record, and media identifiers;
- preserve raw taxon text and source-native taxonomy fields;
- preserve source-native coordinates, uncertainty, obscuration flags, locality text, and precision only in authorized restricted handling;
- do not normalize, geocode, taxonomically reconcile, clip, simplify, generalize, redact, infer, classify, aggregate, or join inside this step;
- do not echo payload values, URLs with secrets, authorization headers, exact coordinates, locality text, or transform parameters into logs.

If capture is partial or the source changes during transfer, return `ERROR` or `QUARANTINED`; do not fabricate completeness.

### Step 7 — Verify transport integrity and bounded completeness

**Goal:** decide whether the captured object is a trustworthy source-native snapshot candidate.

Verify as applicable:

- digest of captured bytes;
- source-published checksum or signature;
- content length;
- archive integrity;
- manifest member coverage;
- page or cursor continuity;
- record count only when contractually meaningful;
- duplicate page/member detection;
- request/response product identity;
- redirect chain and final host;
- media/content types;
- decompression and expansion limits;
- source version/vintage;
- retrieval start/end and source timezone;
- deletion/tombstone representation;
- retry and resumed-transfer semantics;
- readback through an independent path.

Integrity proves bytes or representation consistency. It does not prove botanical truth, rights, sensitivity, taxonomy, evidence, or release.

### Step 8 — Apply source-edge rights, sensitivity, and role disposition

**Goal:** choose only RAW, QUARANTINE, or a fail-closed result.

Route to `QUARANTINE` when any of the following is present or unresolved:

- unknown, mixed, expired, revoked, or record-level rights;
- exact or inferable rare/protected plant location;
- culturally sensitive plant knowledge;
- private-property, access-route, collector, collection-security, or commercial-harvest clues;
- changed obscuration, precision, coordinate uncertainty, or locality detail;
- unexpected source publishers, collections, datasets, media, or terms;
- source-role ambiguity or mixed-role product without an accepted split;
- taxonomy/status drift that could alter downstream claims;
- partial or non-replayable capture;
- schema, content type, manifest, cursor, or endpoint drift;
- missing approved RAW writer;
- receipt or readback failure.

Route to `RAW` only when the accepted source-edge policy and review context allow the exact source-native product to enter RAW. RAW is internal lifecycle state, not public-safe status.

Do not perform public redaction or generalization here unless an accepted source-edge contract explicitly owns that transform. Prefer quarantine and downstream review.

### Step 9 — Write through accepted interfaces and emit the capture handoff

**Goal:** preserve lifecycle and accountability boundaries.

The logical destinations are:

```text
data/raw/flora/
data/quarantine/flora/
```

The current repository does not prove a source-specific accepted writer or physical storage implementation. Therefore:

- call only the accepted writer or adapter;
- do not construct an ad hoc path and copy bytes;
- do not write receipts into payload directories when the accepted receipt family lives elsewhere;
- do not put proof, policy, review, catalog, or release objects in RAW/QUARANTINE;
- record immutable capture identity, source/product identity, request digest, response identity, byte digest, actor, connector version, times, outcome, reason codes, destination reference, and readback result;
- keep secret material and sensitive values out of public or broadly visible receipts;
- link, do not embed, rights and sensitivity review records;
- mark fixture, test, or demonstration material so it cannot be mistaken for source capture;
- stop if the receipt cannot be persisted and read back.

A file appearing under a logical lifecycle directory is not proof that this step closed.

### Step 10 — Read back, reconcile, notify, and stop

**Goal:** finish the source-edge operation without crossing authority boundaries.

1. read back captured bytes/reference, metadata, and receipt through an independent method;
2. recompute and compare identities;
3. verify no unexpected files, logs, temporary objects, or public artifacts remain;
4. verify no write occurred to `WORK`, `PROCESSED`, `CATALOG`, `TRIPLET`, `PUBLISHED`, proof, policy, registry, or release state;
5. record one finite outcome;
6. notify the downstream owning procedure or steward;
7. when material change may affect released claims, open a correction/invalidation handoff without changing release state;
8. cancel retries and revoke temporary credentials or leases as required;
9. stop.

The next transition begins only under its own accepted contract, evidence, and review.

## 8. Rights, sensitivity, geoprivacy, cultural knowledge, and security

### 8.1 Sensitive fields are broader than coordinates

Treat all of the following as potentially location-revealing or restricted:

- latitude/longitude, geometry, geohash, grid cell, parcel, section-township-range, and site code;
- verbatim locality, directions, trail or access notes, landowner, collector route, and habitat description;
- collection event numbers, catalog numbers, media, labels, specimen images, and linked field notebooks;
- observation time precise enough to correlate with other sources;
- elevation, microhabitat, phenology, host association, population size, and survey effort;
- source-native uncertainty, obscuration flags, coordinate precision, and withholding status;
- private-property, lease, easement, permit, restoration site, and access-control information;
- traditional, medicinal, ceremonial, subsistence, or culturally sensitive plant knowledge;
- redaction offsets, jitter seeds, generalization thresholds, reversible transforms, and internal exact-to-public crosswalks;
- joins that reconstruct any of the above.

A payload can be sensitive even when it contains no `geometry` field.

### 8.2 Upstream obscuration and withholding

- never request hidden original coordinates unless the exact controlled-access agreement, purpose, role, storage, reviewer, and audit path authorize it;
- never infer hidden coordinates from tiles, neighboring records, bounding boxes, media metadata, time, elevation, habitat, or repeated requests;
- preserve upstream obscured/private/captive/withheld status;
- never reduce source uncertainty or increase precision;
- treat an upstream public representation as the maximum public precision, not a guarantee that KFM may republish it;
- if obscuration behavior changes, quarantine the affected product and notify sensitivity review.

### 8.3 Record-level and media-level rights

Dataset-level terms may not cover every record or image. Preserve and evaluate:

- originating publisher and institution;
- occurrence/specimen record license;
- media license and creator;
- attribution string and citation requirements;
- dataset key, collection code, catalog number, and source record URL/reference;
- restrictions on redistribution, commercial use, bulk caching, derivatives, and machine learning;
- takedown, correction, and deletion mechanisms;
- consent, agreement, or steward-controlled access references.

Unknown or conflicting rights return `DENY` or `QUARANTINED`.

### 8.4 Culturally sensitive plant knowledge

Open-source or public-source status does not erase community authority or ethical duties.

Before capturing or exposing culturally sensitive knowledge, require:

- the exact knowledge category and purpose;
- authority-to-control or equivalent steward determination where applicable;
- permitted audience and use;
- source and community terms;
- precision and aggregation rules;
- retention and deletion requirements;
- citation and attribution requirements;
- correction, revocation, and withdrawal path.

Do not place restricted cultural knowledge in public PRs, issues, logs, fixtures, documentation examples, or AI prompts.

### 8.5 Taxonomy and status are separate from retrieval

A refresh may reveal changed:

- scientific names and authorships;
- source symbols or taxon identifiers;
- accepted/synonym relationships;
- ranks and concepts;
- nativity, invasive status, or cultivation flags;
- legal or conservation status;
- distribution/checklist values.

Preserve source-native values and notify taxonomy or status review. Do not rewrite accepted KFM concepts or public claims inside source refresh.

### 8.6 Security controls

An accepted live implementation should prove:

- host and scheme allowlists;
- DNS rebinding and redirect controls;
- SSRF and local-resource denial;
- least-privilege credentials;
- secret redaction and no credentials in repository state;
- bounded time, size, records, pages, archive expansion, and retries;
- decompression-bomb and parser-hardening limits;
- content-type and file-signature checks;
- isolated temporary storage and cleanup;
- immutable write or append-only capture behavior;
- restricted-access logging and telemetry;
- cancellation and kill-switch behavior;
- supply-chain pinning for connector dependencies;
- audit event and receipt integrity;
- no public-client or direct-model path to source endpoints or restricted lifecycle stores.

### 9.1 Product rules

For every family:

- one source descriptor may need multiple separately activated products;
- one endpoint may expose products with different rights, roles, sensitivity, cadence, and review requirements;
- one product refresh must not broaden the accepted query or fields;
- a new API version, export format, source publisher, collection, table, or algorithm is a new review event;
- a full product replacement must preserve supersession and deletion semantics;
- a source product may be captured while downstream claims remain stale, abstained, denied, or withdrawn.

## 10. Stale state, supersession, correction, and withdrawal

### 10.1 Stale is not deleted

A missed cadence, failed request, or `NO_CHANGE` result must not silently:

- delete the prior source version;
- mark it current beyond its reviewed freshness policy;
- extend rights or review validity;
- update public release time;
- remove stale UI state;
- overwrite correction or withdrawal state.

Record source freshness independently from release freshness and claim support.

### 10.2 Material source changes that require downstream notification

Notify the correction or owning review path when a refresh reveals:

- source withdrawal, endpoint retirement, or product supersession;
- license, terms, attribution, redistribution, or access change;
- changed publisher, collection, or data provider;
- record deletion, takedown, embargo, or consent revocation;
- changed coordinate precision, obscuration, uncertainty, locality, or media;
- changed taxonomy, conservation status, legal status, or source role;
- materially different counts, geography, time range, or coverage;
- changed algorithm, collection, quality flags, or uncertainty for a derived product;
- compromised integrity, signature, archive, or source-head history;
- changed citation requirements;
- security incident or credential compromise.

A notification does not itself invalidate or roll back a release. It opens the owning governed transition.

### 10.3 Supersession

Never overwrite a source version in place merely because the upstream product is “latest.”

Preserve:

- prior source-head and capture identity;
- new source-head and capture identity;
- source/product supersession relationship;
- retrieval, source, publication, effective, and correction times;
- changed rights/sensitivity/role/cadence posture;
- downstream consumer and release references where known;
- correction or withdrawal handoff.

### 10.4 Upstream deletion and takedown

When an upstream record disappears:

1. record the observation without republishing the deleted content;
2. preserve internal audit evidence only as permitted by rights, consent, retention, and legal policy;
3. notify evidence and correction owners;
4. determine whether downstream claims, tiles, indexes, caches, exports, stories, or AI receipts depend on it;
5. do not restore or expose the content from cache by default;
6. follow separate correction, withdrawal, and rollback procedures.

### 10.5 Operational cancellation versus rollback

- `CANCELLED` ends an in-progress source-edge run.
- QUARANTINE holds captured or candidate material.
- Correction changes or supersedes records and claims.
- Withdrawal removes public support or availability under a release decision.
- Rollback restores a prior released state through the governed release path.
- Reverting this Markdown file changes documentation only.

Do not call every stop a rollback.

## 14. Refresh handoff packet

A reviewable source-edge handoff should contain or reference:

- run ID;
- repository commit and branch;
- runbook path, version, and blob;
- source ID and descriptor version/digest;

- operator and trigger;

- canonical request-scope digest;
- detector type and accepted semantics;
- prior source head;
- observed source head;
- response status and permitted metadata;
- redirect/final-host evidence;
- manifest, cursor, inventory, version, or checksum evidence;
- no-change explanation when applicable.

### 14.3 Capture evidence

- capture/reference identity;
- byte/content digest;
- size, archive member, page, cursor, or record coverage where meaningful;
- completeness and integrity result;
- RAW or QUARANTINE destination reference;
- writer identity and version;
- independent readback result;
- temporary-object cleanup result.

### 14.4 Governance references

- exact accepted source role;
- rights review reference and validity time;
- sensitivity/geoprivacy review reference;
- cultural-authority reference or explicit not-applicable decision;
- cadence/freshness reference;
- credential reference and scope—not the credential;
- policy result reference only if an accepted source-edge evaluator actually ran;
- reviewer/escalation route.

### 14.5 Outcome and follow-up

- one finite procedure outcome;
- public-safe reason codes;
- unresolved questions;
- downstream pipeline/taxonomy/evidence notification;
- stale/correction/invalidation notification;
- cancellation or kill-switch state;
- consumer inventory reference;
- source supersession/withdrawal reference;
- next authorized step;
- explicit statement that no release, deployment, promotion, or publication occurred.

### 14.6 Exclude from broadly visible packets

- API keys, tokens, cookies, authorization headers, or secret-manager values;
- exact sensitive coordinates or locality text;
- hidden source coordinates;
- culturally restricted knowledge;
- private-property, access-route, collector, or collection-security detail;
- reversible transform parameters;
- full restricted payloads or media;
- personal data not required by the approved audit contract.

## 17. Document maintenance and rollback

### 17.1 Updating this runbook

Update the runbook when current repository evidence materially changes:

- accepted Directory Rules or placement;
- source registry topology;
- SourceDescriptor schema or vocabulary;
- activation-decision contract;
- connector identity, command, or live state;
- source rights, sensitivity, or cultural-governance contract;
- RAW/QUARANTINE writer and storage;
- receipt contract;
- source-product tests and workflow;
- policy evaluator and enforcement;
- correction, withdrawal, or rollback procedures.

Do not update current-state claims from memory, a generated summary, an unmerged branch, or a green held workflow.

### 17.2 Documentation rollback before merge

Before merge, rollback is:

1. close the draft PR;
2. delete the feature branch after review;
3. preserve review discussion where useful;
4. make no operational source or lifecycle claim from the abandoned text.

### 17.3 Documentation rollback after merge

After merge, use:

- a reviewed revert of the exact documentation commit; or
- a bounded forward-correction PR.

Do not rewrite shared history.

Reverting this document does not:

- deactivate a source or connector;
- revoke a credential;
- delete captured bytes;
- reverse a lifecycle transition;
- restore a prior descriptor;
- undo a policy decision;
- invalidate a public cache;
- withdraw or roll back a release;
- notify downstream consumers.

Those require their owning procedures.

### 17.4 Operational cancellation and correction

When an actual run is in progress:

- use the accepted kill switch or cancellation path;
- inventory partial requests, temporary objects, leases, credentials, and receipts;
- prevent retries and downstream handoff;
- route partial material to approved quarantine or secure deletion under policy;
- open correction/invalidation review if prior public claims may be affected;
- preserve audit evidence within rights and sensitivity constraints.

Do not use a Git revert as an operational stop control.
