# Settlements and Infrastructure Operational Procedure Boundary

This directory routes maintainers to Settlements/Infrastructure procedures and
states the lane's current fail-closed posture. It is an index and boundary
contract, not municipal-status, census, facility, condition, service,
dependency, source, policy, evidence, proof, rollback, release, or publication
authority.

> [!WARNING]
> KFM is not an emergency, public-safety, utility-service, infrastructure-
> condition, municipal-law, land-use, planning, inspection, security, legal, or
> regulatory authority. Repository files and passing checks cannot establish
> that a place is legally incorporated, a facility is safe, a service is
> available, or infrastructure is current, complete, lawful, or suitable for
> operational decisions.

> [!IMPORTANT]
> Current executable evidence directly tied to this lane contains two bounded
> profiles: static readiness and no-network-compatible EvidenceBundle
> projection convergence. The promotion and rollback runbooks now provide
> repository-grounded preflight and review handoffs, but no profile validates
> real Settlements/Infrastructure records, activates domain policy, produces
> proof, executes rollback, or establishes release, deployment, promotion, or
> publication authority.

## Purpose and inherited authority

Accepted [ADR-0029](../../adr/ADR-0029-adopt-directory-governance-standard-v2.md)
adopts the [Directory Rules](../../doctrine/directory-rules.md), which place
human operational procedures below `docs/runbooks/` and require boundaries to
inherit authority rather than manufacture it.

This README:

- distinguishes implemented readiness and schema-convergence checks from held
  domain semantic work;
- routes readers to current child procedures and responsibility roots;
- preserves settlement and infrastructure, legal and census, source-role,
  temporal, sensitivity, cultural, sovereignty, and cross-domain boundaries;
- records stop conditions for operational or public claims; and
- keeps documentation, validation, review, rollback, release, deployment,
  promotion, publication, and correction as separate states.

It does not resolve the repository's `settlements-infrastructure`,
`settlement`, and related path variants. That remains an ADR- and
migration-dependent question.

## Static readiness

The [domain workflow](../../../.github/workflows/domain-settlements-infrastructure.yml)
performs three read-only jobs:

1. `validate-settlements-infrastructure` checks the expected structural and
   placeholder inventory, then records
   `WORKFLOW_HOLD: semantic Settlements/Infrastructure validation is not established`.
2. `build-proof-settlements-infrastructure` confirms the proof hold and records
   that no accepted deterministic proof producer exists.
3. `publish-dry-run-settlements-infrastructure` checks candidate and published
   boundaries and records that no accepted release-dry-run command or
   candidate-manifest contract exists.

Its readiness helper is:

```bash
python tools/validators/ci_readiness.py \
  --label "Settlements/Infrastructure" \
  --test-root tests/domains/settlements-infrastructure \
  --validator-root tools/validators/domains/settlements-infrastructure \
  --validator-root tools/validators/facilities \
  --validator-root tools/validators/hazard-exposure
```

This helper classifies readiness surfaces; it does not execute placeholder test
modules or validator scripts. Use the exact workflow at the reviewed commit as
the full procedure definition.

A green readiness result means only that the expected paths, parse checks, and
held-state sentinels behaved as written at the tested SHA. It does not prove
legal place identity, facility status, source admission, rights, active policy,
evidence closure, proof, review, rollback, release, or public behavior.

## Bounded EvidenceBundle projection convergence

The
[convergence workflow](../../../.github/workflows/settlements-infrastructure-evidence-bundle-convergence.yml)
verifies that the domain's
[`evidence_bundle.schema.json`](../../../schemas/contracts/v1/domains/settlements-infrastructure/evidence_bundle.schema.json)
remains a projection of the
[shared EvidenceBundle schema](../../../schemas/contracts/v1/evidence/evidence_bundle.schema.json)
rather than a second semantic authority.

Run the complete guarded procedure in
[`NO_NETWORK_TEST_RUNBOOK.md`](./NO_NETWORK_TEST_RUNBOOK.md). Its focused
commands are:

```bash
python -m unittest discover \
  --start-directory tests/validators/domains/settlements-infrastructure \
  --pattern 'test_evidence_bundle_schema_convergence.py' \
  --verbose
python tools/validators/validate_settlements_infrastructure_evidence_bundle_projection.py --fixtures
```

The profile checks projection delegation, selected metadata boundaries, the
shared closed top-level shape, and expected acceptance/rejection behavior over
tracked shared fixtures. It does not establish a materialized EvidenceBundle,
EvidenceRef resolution, source authority, correct rights or sensitivity labels,
active policy, infrastructure review, proof, candidate approval, release,
deployment, promotion, or publication.

The workflow sets `KFM_NO_NETWORK=1`, but it does not inject the shared Python
startup guard into `PYTHONPATH`. The environment value alone is not runner-wide
no-egress proof. The no-network runbook provides the guarded local procedure and
explains its limits.

## Rollback readiness

The [rollback runbook](./ROLLBACK_RUNBOOK.md) now replaces proposal-era live
steps with a repository-grounded readiness and accountable-review procedure.
It can:

- inventory the lane and stop when no exact affected release is established;
- classify `ROLLBACK_CANDIDATE`, `WITHDRAWAL_CANDIDATE`, `HOLD`, or `ERROR`;
- validate a protected candidate against the cross-cutting proposed
  `RollbackCard` schema and validator;
- run the generic and Hazards synthetic rehearsal tests as bounded tool evidence;
- preserve critical-infrastructure, cultural, sovereignty, rights, time,
  evidence, correction, and invalidation requirements; and
- produce a review handoff without mutating public state.

Current limits are material:

- candidate, manifest, rollback-card, proof, rollback-support, and published
  lane inventories contain no instance record or payload;
- no rollback-specific test exists below
  `tests/domains/settlements-infrastructure/`;
- `pipelines/rollback/main.py` remains a one-line greenfield placeholder;
- the synthetic helper refuses non-synthetic roots and scenarios; and
- operational target selection, policy, signatures, independent approval,
  invalidation execution, receipts, alias mutation, deployment, and publication
  remain held.

A green generic RollbackCard validator or synthetic rehearsal is not a
Settlements/Infrastructure release or recovery proof.

## Inputs, outputs, and finite states

### Permitted bounded inputs

- the tracked repository tree at an exact revision;
- required boundary files named by the domain workflow;
- tracked schemas and fixtures inspected by the bounded workflows;
- the domain EvidenceBundle projection and shared EvidenceBundle schema;
- current placeholder test and validator inventories;
- documented policy, proof, candidate, rollback, and published-lane hold markers;
- one public-safe, reference-only candidate dossier for promotion preflight;
  and
- one protected rollback candidate whose exact release references and support
  are independently supplied for readiness review.

### Bounded outputs

- workflow or local-check status tied to an exact commit;
- structural-error messages for missing paths, malformed JSON, unexpected
  maturity, or held-lane drift;
- a promotion preflight result of `PASS`, `ABSTAIN`, `DENY`, `ERROR`, or
  workflow `HOLD`;
- a rollback candidate disposition of `ROLLBACK_CANDIDATE`,
  `WITHDRAWAL_CANDIDATE`, `HOLD`, or `ERROR`; and
- an accountable-review handoff with explicit non-effects.

These outputs are not EvidenceBundles, PolicyDecisions, ReviewRecords, proofs,
PromotionDecisions, ReleaseManifests, approved RollbackCards, correction
completion, rollback execution, release, deployment, promotion, or publication.

### Failure cases

Return or preserve a fail-closed result when:

- a required path, schema, fixture, or candidate cannot be read or parsed;
- evidence, source role, rights, sensitivity, sovereignty, time, identity,
  geometry, proof, policy, review, correction, rollback, or release support is
  unresolved;
- an unexpected substantive test, validator, proof, candidate, manifest,
  rollback card, or published payload appears without reconciled authority;
- a no-network claim exceeds the exact guard and code path that were tested;
- a rollback target is absent, mutable, equal to the affected release, or not
  proven safe now;
- a request would expose restricted geometry, infrastructure detail, cultural
  information, living-person context, credentials, or exploit-relevant text;
- an actor would author and solely approve a policy- or release-significant
  transition without an accepted exception; or
- a command would contact a live source, mutate lifecycle or public state,
  release, deploy, promote, publish, or execute rollback.

## Rights, sensitivity, and cross-domain boundaries

Settlements/Infrastructure material may contain harmful precision or contested
meaning. Preserve at least these distinctions:

- legal municipality, census place, named place, historic townsite, community,
  and map label;
- facility identity, operator, ownership, condition, capacity, service,
  dependency, access, and safety claim;
- canonical restricted geometry and generalized public geometry;
- observation, legal or regulatory record, model, classification, aggregate,
  interpretation, and generated summary; and
- this lane's scope versus Roads/Rail/Trade, Hydrology, Hazards, Archaeology,
  People/DNA/Land, cultural, sovereignty, safety, legal, and emergency authority.

Do not place sensitive coordinates, facility interiors, vulnerability detail,
credentials, or protected review text in public issues, pull requests, logs, or
fixtures. Escalate through the competent authority's established channel when a
real-world safety or emergency response is required.

## Maintenance and verification triggers

Re-open this boundary when any of the following changes:

- a direct child runbook changes classification or command surface;
- substantive domain tests, validators, fixtures, policy, proofs, candidates,
  manifests, rollback cards, rollback support, or published payloads appear;
- a lane-specific release or rollback rehearsal is introduced;
- the generic RollbackCard contract, schema, validator, fixtures, or workflows
  change;
- the no-network guard is wired into the convergence workflow;
- an accepted release dry-run, rollback engine, public resolver, invalidation
  executor, or execution receipt appears;
- accountability or separation-of-duties assignments are adopted;
- source rights, sensitivity, cultural, sovereignty, or infrastructure exposure
  posture changes; or
- the domain identity or path-alias question is resolved.

Until those checks are current, retain the narrowest supported claim and the
existing holds.

correction. Either action changes documentation only. It does not undo source
admission, evidence, policy, lifecycle, rollback, release, deployment,
