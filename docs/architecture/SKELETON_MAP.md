## 1. Role and non-goals

This file answers six practical questions:

1. Which top-level responsibility root owns an artifact?
2. Which lifecycle or accountability lane owns an instance?
3. Which authority must be consulted before a path or behavior changes?
4. Which roots are canonical, platform, compatibility, deprecated, conditional, or absent?
5. Which internal state may cross the public trust membrane?
6. Which validation and rollback evidence is required for a coherent change?

It complements, rather than competes with, [`SYSTEM_MAP.md`](./SYSTEM_MAP.md):

| Document | Primary responsibility | What it should not become |
|---|---|---|
| `SYSTEM_MAP.md` | Conceptual whole-system flow: trust spine, lifecycle, evidence, release, governed delivery, correction | A recursive repository inventory or path registry |
| `SKELETON_MAP.md` | Commit-pinned physical top-level map, adopted root classes, contributor routing, lifecycle lanes, and current drift | Doctrine, machine authority, implementation proof, or a second root registry |
| `docs/architecture/README.md` | Architecture-lane entry point, folder contract, navigation, and convergence status | Whole-system implementation proof |
| `control_plane/root_registry.yaml` | Machine-readable projection of adopted root classes and current classified roots | Human doctrine, source activation, migration authority, or publication authority |

### Non-goals

This map does not:

- create, activate, rename, move, mirror, retire, or delete a root;
- accept or amend an ADR;
- define object semantics, schema fields, policy rules, source roles, or release gates;
- promote a lifecycle object or authorize public exposure;
- claim that every present root or lane is complete, deployed, or clean;
- replace root READMEs, the drift register, validation logs, receipts, proofs, or release records;
- treat historical tree counts or old generated scaffolds as current evidence.

### 5.1 Root admission rule

Before proposing a new root or reviving an absent/retired one, require:

1. one unique project-wide responsibility;
2. proof that no existing canonical root owns that responsibility;
3. an accepted decision when the responsibility model changes;
4. owner, review, exposure, mutability, and retention boundaries;
5. migration, compatibility, validation, and rollback treatment;
6. machine-projection updates only after human authority is established.

A topic name, implementation language, vendor, domain, or large file count is not sufficient root authority.

## 7. Lifecycle and accountability skeleton

The lifecycle shorthand remains:

```text
RAW -> WORK / QUARANTINE -> PROCESSED -> CATALOG / TRIPLETS -> PUBLISHED
```

Promotion is a governed state transition, not a file move, commit, pull request, merge, workflow result, artifact upload, deployment, or GitHub release.

```mermaid
flowchart LR
  source["Source edge"] --> raw["RAW"]
  raw --> work["WORK"]
  raw --> quarantine["QUARANTINE"]
  quarantine --> work
  work --> processed["PROCESSED"]
  processed --> catalog["CATALOG"]
  processed --> triplets["TRIPLETS when applicable"]
  catalog --> gate["Evidence + policy + review + release"]
  triplets --> gate
  gate --> published["PUBLISHED carrier"]
```

### 7.1 Present canonical data lanes

| Lane | Responsibility | Public posture |
|---|---|---|
| `data/raw/` | Admitted source capture or immutable source reference | Internal |
| `data/work/` | Candidate transformation and review work | Internal |
| `data/quarantine/` | Fail-closed held material, reasons, and obligations | Restricted/internal |
| `data/processed/` | Validated internal domain products | Internal until separate release |
| `data/catalog/` | Discovery and provenance projections | Governed; not release authority |
| `data/triplets/` | Optional graph projections | Derived; not sovereign truth |
| `data/receipts/` | Auditable process memory | Internal unless explicitly released |
| `data/proofs/` | Proof-support and validation closure records | Internal unless explicitly released |
| `data/registry/` | Governed registry instances | Mixed exposure by contract and policy |
| `data/published/` | Release-approved public-safe carriers | Governed public path only |

`release/` remains separate from `data/published/`: one stores release and correction **decisions**; the other stores or points to approved carrier **instances**.

### 7.2 Current noncanonical direct data children

The current data tree also contains:

```text
data/document/
data/manifests/
data/maps/
data/prov/
data/reports/
data/rollback/
data/trade-routes/
data/triplet/
data/triplet(s)/
```

These paths are current repository evidence, not new-write authority. Current `data/README.md` classifies them as compatibility, migration, deprecation, or decision candidates that require per-object inventory, producer/consumer cutover, identity preservation, validation, and rollback before movement or retirement.

> [!WARNING]
> Do not “clean up” these lanes by bulk movement. Classify the object family first, then move through a reviewed migration with one canonical writer and proved consumers.

<a id="trust-membrane"></a>

## 8. Governed public path

Ordinary public clients use governed interfaces or released public-safe artifacts. They do not read RAW, WORK, QUARANTINE, candidate stores, canonical internal databases, internal proof stores, or model runtimes as their normal path.

```text
SourceDescriptor / source identity
        |
        v
EvidenceRef -> EvidenceBundle resolution
        |
        v
policy + sensitivity + review + validation
        |
        v
release decision + correction / rollback target
        |
        +-----------------------------+
        |                             |
        v                             v
governed API                     released static carrier
        |                             |
        +--------------+--------------+
                       v
Explorer / map / Evidence Drawer / Focus Mode / export
```

### 8.1 Dynamic crossing

A dynamic response must be bounded by the applicable semantic contract, machine schema, policy outcome, evidence resolution, review/release state, and public response envelope. Runtime outcomes belong to their governing contract; current public response vocabulary is `ANSWER`, `ABSTAIN`, `DENY`, and `ERROR`.

### 8.2 Static crossing

A static PMTiles, COG, GeoParquet, JSON, image, or other carrier requires the applicable manifest, digest/integrity binding, rights and sensitivity posture, release decision, correction state, and rollback or withdrawal route. Static hosting does not bypass the trust membrane.

### 8.3 AI and map boundary

Maps, tiles, graphs, indexes, scenes, dashboards, summaries, and AI answers are downstream carriers or interpretations. `EvidenceBundle` outranks generated language. A renderer or model may help a user inspect released evidence; it cannot establish source authority, policy permission, review, release, or truth.

## 9. Domains are lanes

A domain is normally a bounded lane inside responsibility roots, not a top-level folder.

```text
docs/domains/<domain>/                  human domain architecture and guidance
contracts/domains/<domain>/             semantic domain contracts
schemas/contracts/v1/<family>/          machine shape under the adopted schema route
policy/<domain-or-profile>/              admissibility rules
fixtures/domains/<domain>/               synthetic test inputs
tests/<owned-test-lane>/                  executable conformance
connectors/<source-family>/               source-specific admission implementation
pipelines/<owned-lane>/                   transformations
data/<lifecycle-or-accountability-lane>/  governed instances
release/<decision-family>/                release and correction decisions
```

The exact child path is **NEEDS VERIFICATION** against the root README, existing conventions, accepted ADRs, current consumers, and machine validators before creation. The pattern above is a responsibility crosswalk, not a license to create every listed path.

### 9.1 Cross-domain seams

A cross-domain join or relation does not erase domain ownership. It should identify:

- the owning domain for each object;
- the relation owner or seam contract;
- source-role and scale compatibility;
- temporal and spatial support;
- policy and sensitivity effects;
- evidence resolution;
- review and release obligations;
- correction and rollback propagation.

Derived layers, graph edges, search indexes, and stories do not replace canonical domain evidence.

### 9.2 Sensitive domains

Living-person, genomic, rare-species, archaeology, cultural/tribal, infrastructure, private-land, title, and harmful-precision material fails closed. Use quarantine, redaction, generalization, staged access, delay, abstention, or denial until qualified evidence and authority support a safer posture.

## 10. Cross-root change closure

Use this matrix to identify the directly affected closure set.

| Requested change | Typical direct dependencies | Minimum evidence |
|---|---|---|
| Add or change an object field | Contract, schema, fixture polarity, validator/test, compatibility note, docs | Meaning/shape parity and negative tests |
| Change admissibility or exposure | Policy, fixtures/tests, API/static delivery behavior, docs, review evidence | Fail-closed allow/deny/abstain cases |
| Add a source | Source documentation/descriptor, connector, registry instance, rights/sensitivity review, fixtures, tests, receipts | No-network fixture proof before activation |
| Change a transformation | Pipeline spec, executable pipeline/package, fixtures/tests, receipt binding, rollback | Deterministic replay and negative cases |
| Add a public API capability | Contract, schema, policy, evidence resolution, app implementation, tests, release binding, docs | No internal-store bypass and all finite outcomes |
| Add a map or export carrier | Layer/artifact manifest, evidence/release binding, sensitivity transform, integrity test, correction behavior | Released public-safe artifact proof |
| Change a release object | Release contract/schema/policy, candidate fixtures, validators, proof/catalog closure, correction/rollback | Fail-closed dry run and reversible transition |
| Move or rename a path | Directory authority, identity, inbound links/fragments, writers, consumers, migration record, validation, rollback | No-loss comparison and one canonical writer |

A documentation-only update may explain the closure set. It must not imply that the listed implementation or release work occurred.

### 11.1 Topology validator posture

The directory-governance validator is a deterministic, no-network ratchet. Its baseline records inherited debt; it is not a conformance certificate. Do not regenerate, expand, or weaken the baseline to make an unrelated change green. Classify a failure as introduced, inherited, stale-baseline, or tool/external before remediation.

### 12.2 What a passing result proves

## 13. Maintenance, correction, and rollback

### 13.1 Refresh triggers

Recheck this map when any of the following changes:

- an accepted ADR amends Directory Rules or root classes;
- a top-level directory is created, activated, deprecated, retired, or removed;
- `control_plane/root_registry.yaml` changes;
- a lifecycle/accountability lane is introduced or converged;
- the topology baseline changes materially;
- the governed public path or release/correction boundary changes;
- `SYSTEM_MAP.md` or the architecture-lane contract changes this document's role;
- an accepted document-identity or generator decision is recorded.

### 13.2 Update method

1. Freeze current `main`, root tree, target blob, root registry, data tree, and applicable authority.
2. Compare the real tree with this map.
3. Update only evidence-backed rows and diagrams.
4. Keep current state separate from target state.
5. Repair connected navigation when it becomes false.
6. Run focused and aggregate documentation/topology validation.
7. Open a reviewable pull request; do not merge, release, deploy, or publish by implication.

### 13.3 Correction

When a claim becomes stale, correct the document in place and preserve the evidence checkpoint. Do not overwrite a historical claim with an unlabelled present-tense statement.

### 13.4 Rollback

- **Before merge:** close the draft pull request and abandon the feature branch.
- **After merge:** revert the focused documentation commit or restore prior blob `09440bbe7ac10e0e7b70eee10f4d50f9022f6c4f` through a reviewable pull request.
- No data migration, source deactivation, cache invalidation, release rollback, deployment rollback, or public withdrawal is required for this documentation-only change.
