## 5. Groundwater, water-governance, and property boundaries

Groundwater is the most consequential Sheridan County trust surface because a
county-scale public explanation can easily drift into person-, parcel-, or well-level
claims.

### 5.1 Groundwater source-role separation

Future source admission should keep at least these roles distinct:

| Source role | Can potentially support | Must not be silently converted into |
|---|---|---|
| Hydrogeologic/scientific source | aquifer, trend, measurement, or geologic context | legal water-right status or potability advice |
| Water-governance source | LEMA/GMD jurisdiction, adopted rules, administrative context | individual compliance, ownership, entitlement, or enforcement conclusion |
| Agricultural statistics | county/year aggregates | farm/operator identity or private irrigation behavior |
| Well/water-right records | only whatever use is specifically admitted and policy-cleared | a public person/property lookup surface by default |
| Generated interpretation | explanation of already released evidence | source authority or legal advice |

### 5.2 Default-deny requests

The eventual public system should deny or abstain from requests such as:

- “Show every irrigation well near this address.”
- “Who owns this water right?”
- “How much water may this farmer legally pump?”
- “Is this private well safe to drink from?”
- “Which parcels are overallocated?”
- “Map exact vulnerable groundwater infrastructure.”

A county Focus Mode is not a shortcut around rights, privacy, legal, security, or
source-role review.

## 6. Agriculture, recreation, history, and public safety

### 6.1 Agriculture

Aggregate statistics may be valuable when their year, geography, suppression status,
source role, and limitations remain visible. KFM must not reverse-engineer suppressed
records or turn aggregate irrigation and farm statistics into household, operator, or
parcel-level profiles.

### 6.2 Recreation

A public lake, wildlife area, park, or access point may be represented only with an
explicit currentness boundary. A dated page is evidence of what that source said at
that time, not proof that the site is open, safe, legal, or accessible now.

### 6.3 Historical interpretation

State or local public-history sources can support attributed historical context. They
do not automatically support archaeological interpretation, exact sensitive-place
mapping, burial/sacred-site claims, private access, or unrestricted reuse of source
content.

### 6.4 Hazard and emergency context

FEMA and NWS material may support released contextual products and links to current
authorities. KFM must not provide its own live warning, flood determination,
insurance conclusion, emergency instruction, or infrastructure-vulnerability analysis.

## 7. Finite outcomes and evidence closure

Future Sheridan public/runtime behavior should remain bounded to finite outcomes:

| Outcome | Use |
|---|---|
| `ANSWER` | Released evidence supports the specific public-safe question and policy permits the answer. |
| `ABSTAIN` | Evidence, currentness, rights, authority, temporal fitness, or review is insufficient. |
| `DENY` | The request seeks private wells, individual water rights, property/title information, sensitive locations, infrastructure vulnerabilities, or another prohibited disclosure. |
| `ERROR` | Evidence resolution, contract validation, policy evaluation, or runtime processing failed safely. |

### Candidate boundary reasons from the plan

- `SRC_MISSING`
- `SRC_ROLE_CONFLICT`
- `TEMPORAL_UNFIT`
- `RIGHTS_UNCLEAR`
- `PRIVATE_WELL_OR_WATER_RIGHT`
- `PROPERTY_TITLE_ACCESS`
- `SENSITIVE_LOCATION`
- `LIVE_SAFETY_REPLACEMENT`
- `VALIDATION_ERROR`

These names remain planning vocabulary until reconciled with current contracts and
policy. This README does not create enums or runtime behavior.

### Evidence closure rule

A consequential Sheridan claim should not become authoritative unless its
`EvidenceRef` resolves to an admissible `EvidenceBundle` with appropriate source
role, spatial/temporal scope, rights, sensitivity, policy, review, release, and
correction state.

## 11. Maintenance, correction, and rollback

### Maintenance triggers

Re-review this README when:

- the sibling build plan changes materially;
- Focus Mode placement is resolved by an accepted decision;
- source admission or water-governance policy becomes implementation evidence;
- county source rights, geometry, privacy, or public-safety controls change;
- a Sheridan-specific payload, fixture, API, map, release, correction, or rollback
  artifact is actually implemented;
- the county index changes in a way that affects this lane's repository status.

### Documentation correction

If a repository fact stated here becomes false, correct the README through a normal
reviewable change and preserve the prior Git history. If a sibling plan claim is stale,
update or supersede the plan rather than silently rewriting its lineage from this README.

### Rollback

Before merge, rollback means abandoning or closing the feature branch / pull request.
After merge, use a transparent revert or forward-fix pull request. Do not recreate a
parallel Sheridan authority or rewrite shared history.

> [!IMPORTANT]
> A Git rollback of this README does not withdraw any future public Sheridan data.
> Published corrections require the separate correction, withdrawal, cache,
> supersession, and release mechanisms appropriate to the actual public artifact.
