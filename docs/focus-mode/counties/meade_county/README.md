> **Purpose.** Explain the repository-present Meade County planning lane and the
> evidence, source-role, public-safety, hatchery-operations, groundwater, ecology,
> rights, currentness, review, correction, and rollback conditions that must remain
> visible before any Meade County Focus Mode can become more than a proposal.

> [!IMPORTANT]
> **This directory contains documentation, not a released county product.** The
> tracked build plan and this README do not admit a source, create an
> `EvidenceBundle`, activate Focus policy, implement a governed API route, approve
> a map or AI answer, or create promotion, release, deployment, or publication
> state.

> [!CAUTION]
> **Placement remains a compatibility HOLD.** This README stays at the existing
> singular, snake_case path. Accepted Directory Rules v2 supports a same-path
> human-documentation repair under `docs/`; proposed ADR-0027 cannot authorize a

> [!WARNING]
> **Park, hatchery, groundwater, ecology, and visitor context can become unsafe
> when stale or over-precise.** KFM must not turn dated planning material, cached

> safety, public-health, hatchery-operation, water-supply, water-right, access,

## 5. Source role, rights, and temporal fitness

The build plan names official sources checked on **2026-05-24**. This README preserves
that date as plan lineage. It does not claim those pages have the same content now.

| Source family in the plan | Intended role | Must not be treated as |
|---|---|---|
| Kansas wildlife/parks public pages | Public place, visitor, institutional, and agency context | Perpetually current safety, closure, fire, stocking, ecological, or access truth |
| Hatchery/fish-rearing public pages | Bounded institutional and public-history context | Permission to expose facility operations, water-supply, security, production, or health detail |
| Public-health advisory source | Official-current health/advisory context when freshly resolved | A cached KFM-derived declaration that a water body is safe or unsafe now |
| Groundwater-management authority | Administrative geography and governance context | Private-well condition, aquifer condition at a specific location, water-right status, ownership, or legal advice |
| Generated KFM explanation | Interpretive synthesis over released evidence | Evidence, official authority, operational status, or release decision |

Before a future public answer or layer uses a source, it should close at least:

- source identity and authority role;
- terms, rights, attribution, access, and redistribution posture;
- retrieval and source-effective time;
- spatial and semantic scope;
- sensitivity and operational-detail review;
- `EvidenceRef` resolution to an `EvidenceBundle` where a claim depends on evidence;
- correction and currentness behavior for volatile information.

If those requirements are not closed, the safe outcome is `ABSTAIN` or `DENY`.

## 6. Park, hatchery, groundwater, and ecology safety

### 6.1 Current visitor and public-health information

A dated page capture or plan statement can support a historical observation about what
was displayed when checked. It cannot support the assertion that the same advisory,
closure, fire status, water condition, or visitor restriction applies now.

A future public interface should distinguish at least:

- **historical observation** — what a source said at a recorded retrieval time;
- **current official state** — resolved directly from an approved current source;
- **KFM interpretation** — an explanation that cites the supporting released evidence;
- **unknown/stale state** — visible to the user rather than silently replaced by old data.

### 6.2 Hatchery and infrastructure detail

Public-safe context may identify a public institution and explain an admitted, reviewed
public role. It should not expose or reconstruct operationally useful details about:

- facility security or vulnerabilities;
- operational water-supply configuration;
- internal procedures or biosecurity;
- current production or stocking activity without appropriate public source authority;
- staff, visitors, private records, or other living-person details.

Where the requested precision creates an operational or security risk, `DENY` is the
appropriate default.

### 6.3 Groundwater, wells, rights, and property

Groundwater-management boundaries and agency roles are not interchangeable with:

- measured groundwater condition at an arbitrary point;
- private-well condition or potability;
- ownership, parcel, title, or access rights;
- a water right, permit, allocation, priority, or legal conclusion.

A county map must not imply those determinations through proximity, aggregation, or
AI inference.

### 6.4 Ecology and geoprivacy

Occurrence records, habitat indicators, field observations, imagery, or derived models may
make sensitive locations reconstructible even when individual coordinates are hidden.
Future release review should consider mosaicking, auxiliary layers, labels, zoom levels,
exports, time filters, and cross-layer inference—not only the precision of one feature.

## 7. Finite outcomes and reason-code guidance

Current Focus and runtime surfaces converge on four user-visible outcomes:

```text
ANSWER
ABSTAIN
DENY
ERROR
```

County-specific reason codes remain **PROPOSED** unless accepted by their owning contract
or policy surface. Useful candidate semantics from the sibling plan include:

| Situation | Safe outcome | Candidate reason semantics |
|---|---|---|
| Public place/context claim has released evidence and policy closure | `ANSWER` | evidence-supported public context |
| Current park alert, HAB, closure, fire, or visitor state is stale or unresolved | `ABSTAIN` | current official source required |
| Hatchery operations, facility security, private well, water-right, or sensitive ecology is requested | `DENY` | restricted precision or non-authoritative determination |
| Evidence resolver, policy evaluator, schema, or runtime fails | `ERROR` | trusted result unavailable |

Do not introduce a fifth public outcome simply to express limitations. An `ANSWER` may carry
limitations, obligations, generalization, or stale markers while remaining one of the four
finite outcomes.

## 9. Smallest safe follow-up

The smallest useful next implementation is **not** a live park-status widget or hatchery map.
It is a no-network, synthetic evidence slice proving one public-safe Meade claim can traverse
the current trust surfaces without leaking operational or stale-currentness semantics.

A bounded follow-up should:

1. choose one low-risk public contextual claim from the plan;
2. represent the source role and retrieval/effective time explicitly;
3. resolve an `EvidenceRef` to a synthetic or otherwise approved `EvidenceBundle` fixture;
4. include negative fixtures for stale-current-status inference and operational hatchery detail;
5. prove `ANSWER`, `ABSTAIN`, `DENY`, and `ERROR` normalization through existing shared contracts where they actually exist;
6. avoid live network access, source activation, private data, sensitive ecology, release, deployment, and publication.

Any new file paths for that implementation require a fresh Directory Rules and current-repository
placement check before authoring.

## 12. Maintenance, migration, correction, and rollback

### Maintenance triggers

Re-review this README when:

- the sibling build plan is materially revised or superseded;
- source admission, rights, currentness, policy, or specialist review changes;
- Meade-specific fixtures, contracts, APIs, map surfaces, or release objects become repository evidence;
- county Focus placement is formally resolved;
- a correction or withdrawal changes a claim described by this planning lane.

### Migration

Do not create a second writable Meade county documentation lane. If a future accepted
migration changes the path, preserve history, repair inbound references, update the county
inventory, document compatibility behavior, and keep a clear rollback target.

### Correction

A documentation correction should distinguish:

- correcting repository facts in this README;
- correcting or superseding the sibling plan;
- correcting an admitted evidence object or public claim;
- withdrawing or superseding a released artifact.

Those are different transitions and should not be collapsed into one Markdown edit.

### Rollback

Before merge, rollback is to abandon or close the feature-branch change. After merge, use a
transparent revert or forward-fix pull request against the actual merged commit. Do not rewrite
shared history or recreate parallel authority.
