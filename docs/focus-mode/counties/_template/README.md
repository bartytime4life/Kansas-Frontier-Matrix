A county plan remains non-publishing until independent evidence, rights, sensitivity, schema, policy, review, release, correction, and rollback requirements close through their owning roots.

## Purpose and inherited boundary

This directory exists to hold reusable **human authoring guidance** for county Focus Mode plans. It inherits its authority from `docs/`: it may explain, orient, constrain, and cross-reference. It does not own semantic meaning, machine shape, policy, executable validation, application behavior, evidence, release decisions, or published data.

The sibling template is intended to help an author describe:

- bounded county scope and time;
- participating domain lanes without transferring their authority;
- candidate source families and source roles;
- candidate layers and evidence requirements;
- fail-closed sensitivity defaults;
- promotion prerequisites;
- acceptance checks;
- unresolved questions and ADR triggers.

The template must remain visibly subordinate to the owning responsibility roots. A county plan may reference those roots; it must not duplicate or replace them.

### The durable question

> Can this scaffold help produce a reviewable county planning candidate without implying that identity, evidence, policy, review, release, correction, or publication has already closed?

When the answer is uncertain, preserve the draft, narrow the claim, and return `NEEDS VERIFICATION`, `HOLD`, `ABSTAIN`, `DENY`, or `ERROR` as appropriate. Do not resolve the uncertainty with persuasive prose.

## Template authoring contract

The sibling [`county-build-plan.md`](county-build-plan.md) is a **candidate authoring scaffold**. Its current bytes establish useful prompts and safety language, but they do not settle the canonical destination path or prove compatibility with the current validator.

### 1. Preserve two distinct metadata responsibilities

When a target path is approved and a copy is created, update both:

1. the top KFM Meta Block for document identity, title, owner route, dates, status, related surfaces, and notes; and
2. the marked structured plan-data block in section 12 for county scope, lane key, canonical-path candidates, sensitivity lanes, source families, evidence counters, gates, release refs, and ADR questions.

Do not copy one block's values into the other mechanically. Document metadata and plan assertions are different responsibilities.

### 2. Preserve the structured-block marker

The sibling currently contains one fenced `yaml` block whose first line is:

```text
# === KFM Focus Mode Build Plan: compatibility plan data (NOT CURRENTLY ADMITTED) ===
```

A copied plan must preserve exactly one such marker and one intended plan-data block until an accepted schema/parser change says otherwise. Preserve the explicit non-admission wording; do not relabel the block as validator input. Additional YAML examples should use `text` fences or be kept outside the parser's search boundary.

### 3. Resolve authoring placeholders without inventing authority

Before proposing a county plan for review:

- replace `<County Name>`, `<county-slug>`, `<OWNER>`, and date placeholders;
- replace every `PROPOSED. <prompt>.` authoring prompt with evidence-bounded county content or an explicit open question;
- preserve `PROPOSED`, `UNKNOWN`, and `NEEDS VERIFICATION` labels where implementation or evidence remains open;
- keep sensitive defaults fail-closed;
- do not set release IDs, rollback IDs, promotion gates, layer counts, or evidence closure values unless corresponding repository artifacts exist and were checked.

A draft with zero declared release gates is honest. A document that declares gates passed without evidence is invalid.

### 4. Keep candidate and authority states separate

| Candidate state | What it can mean | What it cannot mean |
|---|---|---|
| Template copied | Authoring started. | County lane accepted or canonical. |
| Placeholders resolved | Draft is human-reviewable. | Evidence or policy closed. |
| Markdown checks pass | Source structure is well formed. | Semantic truth or release readiness. |
| Proposed index validator passes | Declared local grammar matched. | Payload validation, policy permission, or publication. |
| Semantic contract cited | Intended meaning is known. | Machine shape exists or runtime conforms. |
| Payload schema-valid | Shape is valid, when that schema exists. | Evidence sufficiency, review approval, or release. |
| Release records close | A separately governed transition may be authorized. | Authority to bypass correction or rollback. |

### 5. Never put real sensitive examples in the template

Template examples must be synthetic or visibly illustrative. They must not include real living-person identifiers, DNA or genomic material, private parcels, exact archaeology or burial locations, sensitive species coordinates, exact critical assets, credentials, unpublished source excerpts, or unreleased evidence.

## Safe change sequence

Use this sequence before creating or revising a county plan from the scaffold.

1. **Pin current repository evidence.** Record base commit, target template blob, parent/index state, active ADR status, open PRs, and matching task branches.
2. **Classify the requested operation.** New county plan, repair, migration, validation, replacement, or convergence are different tasks.
3. **Check collisions.** Search the current county index, actual county paths, open PRs, branches, aliases, and generated artifacts.
4. **Resolve placement authority.** Use accepted Directory Rules and accepted ADRs. When the singular/plural survivor is unresolved, stop structural work at `HOLD`.
5. **Create a scoped branch.** Never copy directly to the default branch.
6. **Copy only the approved source template.** Preserve history or record the source blob/digest.
7. **Fill both metadata responsibilities.** Update the KFM Meta Block and structured plan data; remove authoring placeholders without inventing closure.
8. **Create only dependency-closed companions.** Add contracts, schemas, fixtures, validators, tests, application surfaces, data records, or release objects only in their owning roots and only when the task authorizes them.
9. **Run deterministic checks.** Markdown/source checks first; accepted contract/schema/validator tests next; negative sensitivity and release checks before higher maturity claims.
10. **Emit provenance.** Bind final authored files to generated receipts where required.
11. **Open a draft PR.** Report introduced versus inherited failures; keep unresolved runtime, release, and publication states explicit.
12. **Stop before governance transitions.** No merge, ADR acceptance, source activation, release, deployment, promotion, publication, or administrative bypass is implied.

## Migration, correction, and rollback

### Structural migration remains held

A singular-to-plural or other county-template migration needs, at minimum:

- an accepted decision selecting the surviving identity and path grammar;
- complete inventory of template, parent, index, county lanes, generated artifacts, links, fragments, imports, validator assumptions, workflows, and external consumers;
- old-to-new identity and path mappings;
- one canonical writer and any bounded dual-read compatibility;
- parser/index/schema/fixture/test convergence;
- content and link parity;
- rollback bytes and a retirement exit criterion;
- zero-writer and zero-consumer proof before retirement or deletion.

This README supplies none of that authority. It only prevents the blank leaf from obscuring the current boundary.

### Documentation rollback

Before merge, close the draft PR and abandon the feature branch. After a separately authorized merge, either:

1. revert the README-and-generated-receipt change together; or
2. issue a bounded forward-correction PR that preserves the prior blank blob, changed bytes, evidence basis, and review trail.

Do not:

- rewrite shared history;
- delete the sibling template as a shortcut;
- copy the full template body into this README;
- create a second writable canonical template;
- mark a legacy path retired without consumer and writer closure;
- use rollback wording as release authority.
