> placeholders, balancing Markdown, or producing valid-looking YAML proves only
> authoring progress. Evidence, rights, sensitivity, contracts, schemas,
> validators, review, release, correction, and rollback remain owned elsewhere.

## 2. Purpose and inherited boundary

This directory exists to hold reusable **human authoring guidance** for a future
state-scale Focus composition. It inherits its authority from `docs/`: it may
explain, orient, constrain, cross-reference, and preserve design lineage. It
does not own semantic meaning, machine shape, policy, executable validation,
application behavior, evidence, release decisions, or published data.

The sibling template is intended to help a future author describe:

- one bounded geographic state composition and its temporal frame;
- a version-pinned domain profile and one reviewed disposition per domain;
- direct state-scale source families and source roles;
- proposed layers and evidence requirements;
- state-to-county comparison rules without rolling county products up as root
  evidence;
- fail-closed sensitivity defaults;
- promotion prerequisites and acceptance checks;
- correction, withdrawal, and rollback obligations;
- unresolved questions and ADR triggers.

Those prompts are useful planning lineage. They become actionable only after the
owning decisions and machine surfaces close.

### The durable question

> Can this scaffold help produce a reviewable state-planning candidate without
> implying that identity, evidence, policy, review, release, correction, or
> publication has already closed?

When the answer is uncertain, preserve the draft, narrow the claim, and return
`NEEDS VERIFICATION`, `HOLD`, `ABSTAIN`, `DENY`, or `ERROR` in the appropriate
state family. Do not resolve uncertainty with persuasive prose.

## 8. Template authoring contract

The sibling [`state-build-plan.md`](./state-build-plan.md) is a **candidate
planning scaffold**. Its current bytes establish useful questions and design
lineage, but they do not settle canonical placement or prove compatibility with
current validators.

### 8.1 Preserve three distinct authoring responsibilities

The sibling currently separates:

1. **document metadata** in the top KFM Meta Block;
2. **human narrative** under sections 1 through 11; and
3. **structured plan data** in the marked YAML block under section 13.

Those responsibilities must not be collapsed.

| Surface | Intended role | Current boundary |
|---|---|---|
| KFM Meta Block | Document identity, title, owners, dates, status, related paths, and notes. | Documentation metadata only. |
| Narrative sections | Human explanation of scope, domains, sources, layers, evidence, safety, composition, promotion, acceptance, and open questions. | Proposed planning prose; every material claim still needs evidence. |
| Section 13 plan-data block | Proposed machine-oriented planning fields such as area, owner, sensitivity, domain coverage, and canonical-path candidates. | Not currently admitted by a state-aware validator. |

Do not copy values mechanically across these surfaces. A document owner is not a
release authority; a path candidate is not accepted placement; a domain row is
not evidence; a release placeholder is not a release record.

### 8.2 Current copy instruction is held

The sibling instructs authors to copy it to a path shaped like:

```text
docs/focus-mode/state/<state-slug>-state/build-plan.md
```

That instruction is **PROPOSED lineage**. It must not be executed as current
placement law because:

- ADR-0028 is not accepted;
- `kansas-state` is not registered;
- the parent state tree requires a future geographic/system-state split;
- accepted Directory Rules v2 does not select that exact target;
- current validator code does not admit `state`;
- consumer, alias, link, migration, and rollback closure is absent.

### 8.3 Current validator language is not implementation evidence

The sibling describes a proposed state extension to the Focus index validator.
The inspected validator implementation is county-only and defines:

```text
county | region | corridor
```

It does not define `state`, parse the state index, or establish a state-template
admission route. The current registry also omits that Focus validator. Therefore:

- do not mark the template validator-clean;
- do not cite its section 13 data as accepted machine input;
- do not create a fake pass record or hand-authored validation receipt;
- do not broaden the validator in this docs file;
- resolve the conflict through the owning contract, schema, validator, fixture,
  test, registry, and decision surfaces.

### 8.4 Placeholder and assertion discipline

Until acceptance and placement close, the safest action is to maintain the
sibling as proposed lineage rather than instantiate it. When future use is
authorized, an author must:

- replace every `<PLACEHOLDER>` and `PROPOSED. <prompt>.` with evidence-bounded
  content or an explicit unresolved item;
- retain `PROPOSED`, `UNKNOWN`, `CONFLICTED`, and `NEEDS VERIFICATION` labels
  where closure is absent;
- leave release, rollback, gate, evidence-count, and owner fields unresolved
  unless corresponding governed artifacts were checked;
- preserve stable anchors only after inventorying inbound links;
- use one accepted structured-block grammar;
- keep examples synthetic and public-safe;
- record exact source, evidence, policy, review, and release references rather
  than prose claims of completion.

## 9. Evidence, policy, and sensitivity boundary

A state plan may identify candidate sources, but each source and claim must
remain subordinate to the governed evidence and policy chain.

```text
candidate source family
  -> source identity and admission
  -> rights, sovereignty, sensitivity, and temporal checks
  -> bounded retrieval and transformation
  -> EvidenceRef resolution to EvidenceBundle
  -> claim-specific policy and review
  -> finite runtime outcome
  -> separately governed release and public projection
```

### Evidence rules

- A source name, URL, agency, map layer, index row, county product, or citation
  placeholder is not an `EvidenceBundle`.
- Statewide support must match the claim's geographic and temporal scope.
- County-granular authoritative records may support a statewide claim when their
  coverage and aggregation are explicit; county Focus summaries or releases are
  not automatically root evidence.
- Conflicting, incomplete, stale, or rights-unclear support must remain visible.
- `EvidenceBundle` outranks generated language.
- An unresolved `EvidenceRef` narrows the result; it must not be filled by AI.

### Policy and sensitivity rules

State scale does not make sensitive data safe. A future plan must fail closed
for, at minimum:

- exact archaeology, burial, sacred, or culturally sensitive locations;
- rare, threatened, or vulnerable species locations;
- critical infrastructure and security-significant assets;
- living-person and household data;
- DNA, genomic, kinship, and identity-linked land information;
- private land or access-sensitive details;
- rights-unclear, sovereign, confidential, or embargoed sources;
- joins that become sensitive only after composition.

Use denial, abstention, redaction, generalization, aggregation, staged access,
delay, or quarantine as appropriate. Record the transform, reason, policy
version, reviewer, and correction implications in their owning surfaces.

### Runtime outcomes remain separate

The current client-facing runtime envelope uses four outcomes:

| Outcome | Bounded meaning |
|---|---|
| `ANSWER` | Evidence, policy, release, and disclosure requirements support a governed response. |
| `ABSTAIN` | Support, currentness, context, rights, or another prerequisite is insufficient. |
| `DENY` | Policy, role, sensitivity, access, or release state blocks delivery. |
| `ERROR` | The system cannot complete safely or deterministically. |

`HOLD` is a placement, review, promotion, correction, or workflow posture; it is
not a fifth runtime outcome. `PASS` and `FAIL` are bounded validator results, not
public truth judgments.

## 10. Lifecycle, review, release, and publication boundary

KFM preserves the lifecycle shorthand:

```text
RAW -> WORK / QUARANTINE -> PROCESSED -> CATALOG / TRIPLETS -> PUBLISHED
```

A template or plan is documentation, not a lifecycle object. Promotion is a
governed transition, not a copy, move, completed checklist, commit, workflow,
pull request, merge, tag, release-page entry, or UI render.

| State family | Required separation |
|---|---|
| Documentation | Explains the intended composition and unresolved work. |
| Source admission | Establishes source identity, rights, provenance, and intake outcome. |
| Evidence | Resolves claim support and bounded uncertainty. |
| Policy | Determines admissibility, sensitivity, role, and disclosure. |
| Validation | Checks a declared contract or invariant; cannot grant release. |
| Review | Records accountable human or governed review; CODEOWNERS is only routing. |
| Lifecycle | Tracks candidate and governed data state. |
| Release | Authorizes one immutable public-safe version through a distinct decision. |
| Correction and withdrawal | Preserves visible post-release change and dependent invalidation. |
| Rollback | Selects an eligible prior released state and records execution. |
| Runtime | Produces one finite client outcome through governed interfaces. |

Public clients and normal UI surfaces must remain downstream of governed APIs or
release-approved public-safe carriers. They must not read RAW, WORK,
QUARANTINE, canonical/internal stores, template files, validator fixtures, or
model adapters as truth sources.

## 15. Migration, correction, and rollback

### Structural migration remains held

A state-template or mixed-state-tree migration needs, at minimum:

- an accepted decision selecting the geographic and system-state authority owners;
- accepted stable scope identity and registered aliases;
- exact source and target paths under current Directory Rules;
- inventory of templates, indexes, sibling docs, links, fragments, imports,
  parsers, workflows, generated artifacts, applications, and external consumers;
- one canonical writer and bounded read compatibility;
- old-to-new identity and path mapping;
- contract, schema, fixture, validator, test, and registry convergence;
- content, link, and behavior parity checks;
- correction and rollback bytes;
- retirement criteria with zero-writer and zero-consumer evidence.

This README supplies none of that authority. It prevents the blank leaf from
obscuring the current boundary.

### Documentation correction

A correction to this page should:

1. pin the affected version, commit, and blob;
2. identify the false, stale, or conflicted claim;
3. cite the newer decision, contract, schema, test, log, or runtime evidence;
4. update direct-child inventory only after verifying it;
5. preserve useful anchors where feasible;
6. state whether the sibling template or parent state docs also need correction;
7. avoid changing machine or policy authority through prose.

### Rollback

Before merge, close the draft PR and abandon the feature branch. Branch deletion
is a separate action.

After a separately authorized merge, either:

1. revert this README to prior blob
   `8b137891791fe96927ad78e64b0aad7bded08bdc`; or
2. issue a bounded forward-correction PR that preserves the prior bytes,
   evidence basis, rationale, and review trail.

Do not:

- rewrite shared history;
- delete or duplicate the sibling template as a shortcut;
- create a second writable canonical template;
- mark a state path accepted, deprecated, or retired without decision and
  consumer closure;
- use documentation rollback wording as release or public rollback authority.

Because this revision is documentation-only, repository rollback affects this
README. Any future public state product would require its own correction,
withdrawal, cache invalidation, supersession, and rollback process.
