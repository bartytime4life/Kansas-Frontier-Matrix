## 2 · Official ISO Family Baseline

The following currentness statements were checked against official ISO pages on 2026-08-18. They establish upstream publication state only; they do not establish KFM adoption or implementation.

| Standard | Current upstream state | KFM relevance |
|---|---|---|
| [ISO 19115-1:2014](https://www.iso.org/standard/53798.html) | Published Edition 1; remains current; two published amendments; stage 90.92, “to be revised” | Fundamental conceptual model for metadata about geographic information and services |
| ISO 19115-1:2014/Amd 1:2018 | Published amendment | Part of the exact current fundamentals baseline when a conformance target includes it |
| ISO 19115-1:2014/Amd 2:2020 | Published amendment | Part of the exact current fundamentals baseline when a conformance target includes it |
| [ISO/AWI 19115-1, Edition 2](https://www.iso.org/standard/91591.html) | Approved work item under development; intended to replace the 2014 edition | Watch item only; it is not a published replacement and must not silently govern current validation |
| [ISO 19115-2:2019](https://www.iso.org/standard/67039.html) | Published Edition 2; confirmed in 2024; one amendment | Acquisition and processing metadata, including imagery and gridded-data concerns |
| [ISO 19115-2:2019/Amd 1:2022](https://www.iso.org/standard/78888.html) | Published amendment | Must be named when included in an acquisition/processing conformance target |
| [ISO 19115-3:2023](https://www.iso.org/standard/80874.html) | Published current XML implementation | Defines integrated XML Schema and Schematron artifacts for the 19115-1 and 19115-2 conceptual models |
| [ISO/TS 19115-3:2016](https://www.iso.org/standard/32579.html) | Withdrawn on publication of the 2023 edition | Legacy migration reference only; not the current XML baseline |
| [ISO 19157-1:2023](https://www.iso.org/standard/78900.html) | Published current data-quality standard | Companion authority for quality concepts; does not itself define acceptable KFM quality thresholds |

### 2.1 Currentness rules for KFM documentation

1. A future conformance claim must name the exact **part**, **edition**, applicable **amendments**, and—when machine encoding is claimed—the **encoding edition**.
2. A draft or approved work item does not supersede the current published edition until ISO publishes the replacement.
3. A reference to `ISO/TS 19115-3:2016` must be labeled **withdrawn / legacy** unless it is documenting migration from that edition.
4. `ISO 19115` by itself is an imprecise family reference, not a complete machine-conformance target.
5. A national, regional, agency, or KFM profile must be named and versioned when the claim depends on that profile. A profile is not required merely to discuss the base standard, but profile-specific conformance cannot be implied from base-standard validation.
6. ISO publication state and KFM adoption state remain separate axes.

### 2.2 Copyright and implementation boundary

ISO standards are protected works. This page paraphrases public official descriptions and records identifiers, editions, and lifecycle state. A future implementation must obtain and use ISO materials under applicable terms; this repository update does not vendor schemas or reproduce normative clauses.

## 3 · Position in the KFM Standards Stack

ISO 19115 is an external metadata conceptual-model family. KFM's current bounded catalog work uses STAC/DCAT/PROV carrier shapes in synthetic, non-public closure packets. An ISO relationship therefore needs an explicit mapping and conformance boundary; it must not be inferred from the presence of STAC, DCAT, PROV, or similar fields.

## 5 · Candidate ISO-to-KFM Concept Mapping

> [!CAUTION]
> The table below is a **PROPOSED semantic mapping aid**, not a field-level contract. ISO 19115 is a conceptual model with conditionality, associations, code lists, multiplicity, and profile rules. STAC/DCAT/KFM projections are not lossless substitutes. Exact bindings require a selected normative target, consumer, mapping contract, fixtures, and tests.

| ISO concept family | Candidate KFM source | Candidate exchange projection | Boundary |
|---|---|---|---|
| Resource identification and citation | `SourceDescriptor`, governed catalog record, release metadata | STAC Item/Collection identifiers and titles; DCAT identifiers and titles | Identifier equivalence must be decided per object family; `spec_hash` is not automatically a citation identifier |
| Resource scope and hierarchy | Source/dataset/version contracts | STAC Collection/Item relations; DCAT Dataset/Distribution relations | Dataset, series, service, feature, and file scopes must not be collapsed |
| Responsible party | Publisher/steward fields in `SourceDescriptor` and governed review records | DCAT publisher/contact projection or ISO responsibility role | A contact or publisher is not automatically the KFM release authority |
| Spatial extent | Governed geometry/extent fields on domain and catalog records | STAC geometry/bbox; DCAT spatial coverage; ISO geographic extent | Geometry precision, CRS, and sensitivity transforms must remain explicit |
| Temporal extent and dates | Domain temporal authority plus source/retrieval/release/correction times | STAC datetime/interval; DCAT temporal; ISO extent/citation dates | Observation, valid, publication, retrieval, revision, and correction time are distinct |
| Distribution and transfer | Released artifact and `ReleaseManifest` | STAC assets; DCAT distributions; ISO distribution/transfer options | Access URL is not release authority; byte digest, rights, and release state remain required |
| Lineage and process history | `EvidenceBundle`, `RunReceipt`, correction lineage | PROV projection; ISO lineage/process-step view | A lineage string is a lossy summary; evidence and receipts remain authoritative |
| Data quality | Validation reports, method records, domain quality objects | ISO 19157-aligned quality view; bounded STAC/DCAT quality summaries | ISO quality description does not set acceptable thresholds or approve release |
| Reference system | Governed CRS/datum metadata | STAC projection extension or ISO reference-system view | CRS identifiers and axis/order semantics require exact validation |
| Maintenance and revision | Source cadence, release state, correction/supersession records | ISO maintenance view; catalog update metadata | Cadence is not freshness proof; stale and withdrawn states must propagate |
| Legal and security constraints | Rights/sensitivity policy, source terms, review obligations | ISO legal/security constraint view | Projection is descriptive and potentially lossy; KFM policy remains authoritative |
| Acquisition and processing | Source/instrument/acquisition metadata plus `RunReceipt` | ISO 19115-2 view; STAC EO/raster or domain extensions where applicable | A source-native acquisition record must not be invented from a derived artifact |

### 5.1 Required mapping properties

Any future field-level crosswalk should record, for every mapping:

- source object and exact field/path;
- target ISO part, edition, class/property, code list, and multiplicity;
- direction (`KFM -> ISO`, `ISO -> KFM`, or both);
- transform function and normalization rules;
- required source role and lifecycle state;
- lossiness (`lossless`, `partial`, `summary`, or `not representable`);
- rights/sensitivity and precision effect;
- null/unknown/conflict behavior;
- identifier and digest semantics;
- correction and supersession behavior;
- fixture IDs and validator assertion; and
- accountable owner and review evidence.

## 6 · Model, Profile, Encoding, Record, and Conformance

Conformance language is unsafe when these layers are collapsed.

| Layer | Meaning | Example | KFM requirement before claiming it |
|---|---|---|---|
| Conceptual model | Abstract classes, associations, properties, code lists, and constraints | ISO 19115-1 and ISO 19115-2 | Exact edition/amendments identified; semantic mapping reviewed |
| Application profile | A community-specific subset, obligation set, extension set, and guidance | A national, agency, domain, or future KFM profile | Profile authority, identifier, version, cardinality, code lists, and governance accepted |
| Encoding | Machine representation of the model/profile | ISO 19115-3:2023 XML Schema and Schematron | Encoding edition, namespace set, schema provenance, and validation toolchain pinned |
| Metadata record | One concrete metadata instance | One XML record or governed JSON projection | Subject identity, scope, source, rights, evidence, and release binding established |
| Mapping/crosswalk | Transformation between models or carriers | KFM/STAC/DCAT/PROV to ISO view | Direction, lossiness, transforms, fixtures, and correction behavior explicit |
| Validation result | Evidence that a specific record passed a bounded rule set | XSD + Schematron + profile checks | Validator version, normative target, inputs, outputs, digest, and negative tests recorded |
| Interoperability result | Evidence that a named producer and consumer exchanged records successfully | KFM exporter to a named catalog | Exact revisions, transport, acceptance criteria, observed run, and limitations recorded |
| Release/publication | Governed exposure of an approved artifact | Released metadata distribution | Evidence, policy, review, manifest, correction, withdrawal, and rollback closure complete |

### 6.1 Minimum claim grammar

Prefer precise statements:

- “This record validated against ISO 19115-3:2023 XSD and Schematron artifacts, plus profile X version Y, using validator Z at revision R.”
- “This mapping covers the listed identification, extent, distribution, and lineage concepts; rights/CARE content remains a KFM extension and is not fully represented in the ISO view.”
- “Interoperability was observed with consumer C for fixture set F; broader consumer compatibility remains unknown.”

Avoid unbounded statements:

- “KFM is ISO compliant.”
- “This dataset is ISO certified.”
- “STAC is equivalent to ISO 19115.”
- “The XML validates, therefore publication is allowed.”

## 7 · Rights, Sensitivity, Sovereignty, and CARE Boundary

ISO 19115 includes metadata concepts for legal, security, and other constraints. Those concepts can carry descriptive information, but they do not replace KFM's source terms, rights decision, sensitivity classification, sovereignty/authority-to-control review, or release policy.

| Concern | Candidate ISO-facing representation | KFM authority that must remain resolvable |
|---|---|---|
| License and use conditions | Legal/use-constraint metadata and citation to authoritative terms | `SourceDescriptor`, rights evidence, exact license/terms version, policy obligations |
| Access restrictions | Access/security constraint metadata | Sensitivity policy, access role, review decision, release scope |
| Precise or harmful location | Generalized extent plus a statement that transformation occurred | Original protected geometry, transform receipt, public-safe geometry, reason and reviewer |
| Indigenous/community authority | Profile extension or external reference where the selected profile permits it | Steward/authority-to-control evidence, consent/obligations, sovereignty review |
| Living-person, genomic, archaeology, rare-species, or infrastructure data | Restricted/generalized public metadata or no public record | Domain policy, qualified review, redaction/generalization, staged access or denial |
| Correction and withdrawal | Maintenance/revision metadata and replacement links | KFM correction notice, withdrawal state, release supersession, cache/search/map/AI propagation |

> [!WARNING]
> A down-projected ISO constraint string is not evidence that CARE, sovereignty, consent, privacy, geoprivacy, or KFM sensitivity obligations were satisfied. Any consequential consumer must resolve the governed KFM evidence and policy state rather than act on the projection alone.

### 7.1 Fail-closed rules

A future ISO export or import must hold, abstain, restrict, generalize, quarantine, or deny when:

- rights or source terms are unknown;
- the responsible authority or source role is unresolved;
- the profile cannot represent a material obligation without loss;
- exact geometry would expose sensitive or harmful precision;
- a source record conflicts with KFM evidence or correction state;
- the target consumer would strip mandatory KFM obligations; or
- release, correction, withdrawal, or rollback binding is missing.

<a id="8--candidate-interoperability-paths"></a>

## 8 · Candidate Interoperability Paths

The existence of an ISO standard does not choose a runtime path. Each path needs a named use case, owner, consumer, and acceptance boundary.

### 8.1 KFM-to-ISO export view — PROPOSED

```text
released KFM object
  -> resolve source + EvidenceBundle + rights/sensitivity + correction state
  -> apply reviewed KFM-to-ISO mapping
  -> emit profile-specific record
  -> validate encoding + profile + KFM obligations
  -> bind receipt and conformance evidence
  -> deliver to named governed consumer
```

This is the safest first interoperability direction because KFM remains the authority for its own source, evidence, policy, and release state. The ISO record is a derived exchange view, not a new canonical store.

### 8.2 ISO-to-KFM source intake — PROPOSED

```text
external ISO record
  -> SourceDescriptor and source-admission checks
  -> immutable capture / digest
  -> encoding + profile identification
  -> parse to WORK candidate
  -> preserve unmapped content and loss report
  -> validate source role, identity, rights, sensitivity, time, and geometry
  -> evidence review / quarantine as needed
```

An ISO-valid record can still be stale, incorrect, unauthorized, over-precise, or unsuitable for KFM. Validation therefore cannot bypass source admission or evidence review.

### 8.3 Federated catalog exchange — NEEDS VERIFICATION

A federation target should be named before KFM chooses a profile, XML serialization, endpoint, or compatibility commitment. Consumer-driven evidence should answer:

- Which catalog, clearinghouse, agency, archive, or tool consumes the record?
- Which exact profile and version does it require?
- Does it require XML, an API, file delivery, or another transport?
- Which fields are mandatory, conditional, ignored, or extended?
- How does it represent corrections, withdrawals, restricted records, and non-public resources?
- Can it preserve KFM rights, sensitivity, and evidence links?

<a id="9--proposed-conformance-and-validation-plan"></a>

## 9 · Proposed Conformance and Validation Plan

> [!IMPORTANT]
> The prior `catalog_metadata_conformance_report` JSON example is **design lineage only**. Repository search did not establish it as a current contract, schema, fixture, validator, or emitted artifact. A future implementation must reuse existing outcome and authority conventions rather than creating a parallel trust object in documentation.

### 9.1 Dependency-ordered graduation

| Phase | Required evidence | Explicit non-effect |
|---|---|---|
| 1. Consumer and target decision | Named producer, consumer, resource scope, ISO parts/editions/amendments, profile, encoding, transport, rights constraints | Does not create a profile or implementation |
| 2. Semantic mapping contract | Reviewed concept/field mapping, direction, lossiness, identifier semantics, null/conflict behavior, correction rules | Does not make machine records valid |
| 3. Machine profile/shape | Versioned XSD/Schematron/profile binding or other approved machine projection in the canonical schema authority | Does not prove producer or consumer behavior |
| 4. Fixture family | Supported, missing-required, invalid-code-list, wrong-scope, rights-unknown, sensitivity, stale, corrected, withdrawn, digest-mismatch, and unsupported-profile fixtures | Synthetic success does not grant release |
| 5. Deterministic validator | No-network where practical; pinned normative artifacts; stable reason codes; exact input/output digests; no mutation | Validator success does not decide policy or release |
| 6. Producer and consumer proof | Export/import implementation, replay, round-trip/loss report, observed named-consumer result | One consumer does not prove universal interoperability |
| 7. Governed release | Evidence/proof closure, policy, authorized review, `ReleaseManifest`, correction, withdrawal, rollback, and public-safe delivery | Merge or deployment alone is not publication authority |

### 9.2 Minimum conformance evidence

A future conformance result should identify at least:

- subject record and governed resource identity;
- ISO part(s), edition(s), amendment(s), encoding, and profile identifier;
- normative artifact provenance and digest where licensing permits local validation;
- validator name, version, code revision, configuration, and execution time;
- XSD, Schematron, profile, mapping, and KFM-obligation results kept distinct;
- stable findings with severity and machine-readable reason codes;
- source/evidence/release references and subject digest;
- rights/sensitivity and lossiness summary;
- correction/supersession relationship;
- producer and intended consumer; and
- explicit statement of what the result does **not** authorize.

### 9.3 Required negative tests

At minimum, fail or hold safely for:

- unspecified part/edition/profile;
- use of withdrawn ISO/TS 19115-3:2016 as the current encoding;
- missing mandatory or conditional content under the selected profile;
- invalid code-list or namespace value;
- incorrect resource scope or hierarchy;
- contradictory spatial or temporal extent;
- source/evidence/release identity mismatch;
- digest or receipt mismatch;
- unknown rights or sensitivity;
- over-precise protected geometry;
- stale, corrected, withdrawn, or superseded subject state;
- lossy mapping presented as lossless;
- external consumer rejection; and
- network or parser failure without an unsafe fallback.

### 9.4 Validation outcome boundary

No new ISO-specific outcome vocabulary is established here. A future contract must align with accepted KFM finite outcomes and distinguish:

- machine validity;
- mapping completeness/lossiness;
- source/evidence status;
- policy/review status;
- interoperability observation; and
- release/publication status.

These axes must not be collapsed into one `compliant: true` flag.

## 11 · Adoption and Conformance Claim Ladder

Use the narrowest claim supported by evidence.

| State | Evidence needed | Permitted statement |
|---|---|---|
| Reference only | Current official standard identifier and bounded guidance | “KFM documents the ISO 19115 relationship.” |
| Mapping draft | Reviewed candidate mapping with explicit gaps and lossiness | “A candidate KFM-to-ISO mapping exists for the listed concepts.” |
| Profile decided | Accepted authority names exact parts, amendments, profile, encoding, scope, and obligations | “KFM has adopted profile X version Y for scope S.” |
| Machine profile implemented | Shape/binding, fixtures, validator, deterministic tests, and negative cases | “Records in fixture family F pass the bounded profile validator.” |
| Producer implemented | Export/import code and replay evidence at an exact revision | “Producer P emits records for scope S under profile X.” |
| Consumer interoperability observed | Named consumer accepts representative records under stated conditions | “Interoperability was observed with consumer C for test set F.” |
| Released | Governed release, evidence/proof closure, policy/review, correction, withdrawal, and rollback | “Release R includes records validated to profile X.” |
| Published | Public-safe delivery and observed public endpoint state | “Endpoint E serves release R under the stated public scope.” |

At the evidence snapshot, KFM is at **reference only**, with **mapping backlog** and bounded non-ISO catalog-closure fixtures. Higher claims remain unestablished.

<a id="8-anti-patterns"></a>
<a id="12--anti-patterns"></a>

## 12 · Anti-Patterns

- **Badge as authority.** An “ISO 19115 ✓” badge without a resolvable conformance result, evidence, policy/review, and release binding is decoration.
- **Family-name ambiguity.** Claiming “ISO 19115 compliant” without the exact part, edition, amendments, encoding, scope, and profile where applicable.
- **Stale encoding baseline.** Treating withdrawn ISO/TS 19115-3:2016 as the current XML implementation.
- **Draft as current law.** Applying ISO/AWI 19115-1 Edition 2 as though it already replaced the published 2014 edition.
- **Crosswalk as truth.** Treating an ISO-shaped view as the canonical KFM source, evidence, policy, or release record.
- **Constraint flattening.** Converting rights, sovereignty, consent, sensitivity, or CARE obligations into one free-text constraint and declaring them satisfied.
- **XML detour.** Adding XML because an encoding exists, without a named producer/consumer requirement and lifecycle cost model.
- **Validation collapse.** Treating XSD/Schematron success as evidence sufficiency, policy allow, review approval, release authorization, or publication.
- **Synthetic overreach.** Treating fixture-only STAC/DCAT/PROV closure as ISO implementation or public catalog proof.
- **Ingest/release collapse.** Letting a valid external ISO record bypass `SourceDescriptor`, evidence review, rights/sensitivity checks, or quarantine.
- **Lossless-by-assumption.** Failing to record unmapped content, multiplicity changes, code-list translations, precision loss, or unsupported extensions.
- **Parallel authority.** Creating ISO-specific contracts, schemas, policy, fixtures, reports, or release records in a convenience directory instead of their owning responsibility roots.
- **Silent correction.** Regenerating exchange records without preserving supersession, withdrawal, correction, and prior-release lineage.
- **Search overclaim.** Treating absence from bounded repository search as proof that no external or unindexed implementation exists.

<a id="appendix-a--reviewer-checklist"></a>

## Appendix A · Reviewer's Checklist

Before approving any KFM statement that asserts ISO 19115 profile adoption, machine conformance, or interoperability:

- [ ] Is the exact ISO part, edition, amendment set, encoding, profile, resource scope, and claim scope named?
- [ ] Is the upstream status current at a dated official-source review?
- [ ] Is withdrawn ISO/TS 19115-3:2016 excluded from current-baseline claims?
- [ ] Is a reviewed semantic mapping contract present with direction and lossiness?
- [ ] Is the subject identity bound to source, evidence, receipt, and release identities?
- [ ] Are rights, sensitivity, sovereignty, consent, CARE, and harmful-precision obligations preserved outside any lossy ISO projection?
- [ ] Are normative validation artifacts and the validator/toolchain pinned and legally usable?
- [ ] Do positive and fail-closed negative fixtures cover the selected profile and KFM obligations?
- [ ] Is the result bounded separately for syntax, profile, mapping, source/evidence, policy/review, interoperability, and release?
- [ ] Is producer-consumer behavior observed at exact revisions rather than inferred from docs?
- [ ] Are correction, withdrawal, supersession, and rollback paths tested?
- [ ] Does the claim avoid turning a badge, document, commit, PR, fixture, or validator pass into publication authority?

If the evidence does not support the requested claim, narrow it or abstain.
