|---|---|
| Exploratory packet identity, clustering, and disposition | `docs/intake/` |

| Executable validators, probes, and reconciliation tools | `tools/` |
| Reusable implementation | `packages/` |

## Unsafe direct transfers

| Packet pattern | Why direct transfer is unsafe | Required correction |
|---|---|---|
| “Ready-to-commit” paths, schemas, validators, policies, and workflows | Packet trees can duplicate or conflict with accepted responsibility roots and current contracts. | Re-derive each artifact from Directory Rules and the current owning lane. |
| Shallow key sorting treated as canonical JSON | Recursively nested values, numbers, Unicode, and cross-runtime behavior can produce different identities. | Use the accepted canonicalization profile and test vectors; keep hash purpose explicit. |
| ETag or remote identifier treated as content identity | Provider metadata may be weak, mutable, absent, or scoped differently from artifact bytes. | Preserve provider identifiers as observations and compute the accepted digest over received bytes. |
| Signature, transparency-log, or Merkle success treated as truth or release | Integrity and signer identity do not prove evidence sufficiency, rights, policy, review, or publication approval. | Keep proof, evidence, policy, review, release, correction, and rollback independent. |
| Network key or log lookup required for every verification | Availability failure can become a hidden fail-open or prevent historical/offline verification. | Define pinned trust material, freshness, revocation, offline behavior, and explicit finite outcomes. |
| Required evidence bundle unresolved but partial claim still emitted | A composed claim can overstate support when one mandatory dependency is missing or denied. | Declare dependency semantics and return a qualified result or `ABSTAIN`, `DENY`, or `ERROR`. |
| Retried event directly invokes an external side effect | At-least-once delivery can duplicate releases, messages, writes, or review transitions. | Reserve and record effects against deterministic event identity before execution. |
| `approve_with_obligation` treated as immediate release approval | An obligation that is not applied, tracked, satisfied, expired, or waived can silently disappear. | Block consequential transition until a governed obligation-closure decision is complete. |
| Correction implemented by overwriting prior evidence or decision state | History, signatures, reasons, and downstream impact become unauditable. | Append a correction or supersession edge and preserve prior objects. |
| Real taxa, coordinates, names, notes, keys, tokens, or reviewer identities in fixtures | Examples can expose sensitive data or normalize unsafe test practices. | Use synthetic, non-joinable fixtures and secret references only. |

## Dependency-ordered continuation

### Wave 1 - meaning and authority decisions

1. Define custody handoff identity, accepted/rejected/duplicate accounting, and reconciliation closure.
2. Define composed-claim dependency roles and finite closure outcomes.
3. Resolve trust-root registry ownership, versioning, revocation, historical verification, and offline behavior.
4. Define deterministic event identity, effect reservation, effect result, and replay semantics.
5. Define conditional-decision obligation application, satisfaction, waiver, expiry, reopening, correction, and release blocking.

### Wave 2 - bounded offline proofs

After the applicable Wave 1 decision closes, admit at most one dependency-closed proof:

- a synthetic sender/receiver custody handoff with partial acceptance, duplicate, rejection, retry, and reconciliation;
- a synthetic composed claim with required, optional, alternative, denied, missing, and contradictory evidence;
- a synthetic signing history with active, rotated, revoked, unknown, and historically valid keys;
- a synthetic at-least-once event replay proving exactly one recorded side effect; or
- a synthetic conditional review decision whose release remains blocked until every required obligation closes.

### Wave 3 - lane adoption

Lane-specific pipelines, signing providers, transparency services, event brokers, review consoles, and release gates remain later work. Each requires:

- an accepted owner and responsibility root;
- current contracts, schemas, policies, fixtures, and validators;
- source, rights, sensitivity, and key-custody review where applicable;
- failure, replay, correction, rollback, and withdrawal behavior; and
- separate exact authorization.

### Recommended next bounded action

**PROPOSED:** start with a contract-only composed-claim dependency profile and synthetic fixtures for `required`, `optional`, `one_of`, `excluded`, `missing`, `denied`, and `contradictory` evidence. This closes a high-leverage claim-meaning gap without introducing live sources, keys, event infrastructure, or publication authority.
